# 관리자 화면 전환 지연 진단

## 결론과 한계

Next.js의 화면 이동은 사용하고 있다. 그러나 새 탭 탐색에서는 개인 목록을 서버에서 다시 읽으므로
모든 화면이 캐시만으로 즉시 뜨는 구성은 아니다. 탭 전환용 최소 로딩시간은 없으며 실제 지연의
밀리초·네트워크/DB/JS 비율은 측정하지 않았다. 사용자 요청대로 코드와 로컬 정보만 확인했다.

## 현재 연결

- `admin-navigation.tsx` → `GuardedLink` → `next/link`: 일반 탐색이며 prefetch를 끄지 않았다.
- `next.config.ts`에는 재사용 시간 변경이 없다. 설치한 Next.js 16.2.12의
  `config-shared.js` 기본값은 dynamic 0초·static 300초다. 동적 경로의 자동 prefetch는
  공통 레이아웃/로딩 뼈대까지만 준비할 수 있다. 뒤로·앞으로 복원은 새 Link 탐색과 구분한다.
- 인증·공용 단어장 읽기의 React `cache()`는 같은 서버 요청 안에서 중복만 제거한다.
  다음 탭 이동까지 개인 목록을 보존하는 캐시가 아니다.
- 학생·배정·성적 등의 개인 조회는 요청 간 공유 캐시에 넣지 않는다. 현재 첫 화면 서버 자료 뒤
  조건이 그대로인데 동일 API를 자동 재조회하는 이중 호출은 발견하지 못했다.

| 화면 | 새 서버 요청의 주요 자료 조회 |
| --- | --- |
| 개요 | 초기 내역 묶음 RPC 1회 |
| 학생 | 첫 10명·필터 RPC 1회 + 접힌 학생 등록용 단어장·분류 조회 2회 |
| 단어시험 | 첫 10명·필터 RPC 1회; 검토 초안 주소에서만 초안 추가 |
| 내역 | 보관 포함 초기 내역 묶음 RPC 1회 |

위 표는 인증 이후 주요 자료 조회다. 세션 함수 호출을 외부 인증 요청 횟수로 단정하지 않는다.
학생 등록 조회는 학생 목록과 별도 Suspense라 목록을 직렬로 막지는 않지만 닫혀 있어도 실행된다.

## 로딩·JS·타이머 구분

- 공용 경로 로딩은 높이 260px 공간을 즉시 표시한다. 짧은 대기도 크게 보일 수 있으나 응답이
  끝나고 일정 시간을 더 기다리는 최소 유지 타이머는 없다.
- 학생/배정 검색 250ms, 내역 검색 300ms는 입력 후 요청을 모으는 시간이며 탭 전환 대기가 아니다.
- 배정창의 `next/dynamic` JS는 첫 열기에서 별도로 불러오고 준비 요청 중 미리 읽는다.
  네 개 관리자 탭의 모든 반복 로딩을 이 JS 하나로 설명할 수는 없다.
- 저장하지 않은 편집을 버리겠다고 승인한 특수 경로는 전체 문서 이동을 쓴다.
  일반 탭 이동과 다르며 이탈 보호를 삭제하면 편집 상태가 손실될 수 있다.

## 개선 순서 제안 — 아직 구현하지 않음

1. 접힌 학생 등록 자료를 등록 영역을 펼칠 때 읽도록 미룬다. 인증/성적 정책 변경 없이 불필요한 조회를 줄인다.
2. 큰 공통 로딩 화면을 화면별 뼈대로 안정화한다. 체감 깜박임 개선이며 DB 비용 감소와 구분한다.
3. 같은 관리자·같은 조건의 최근 목록을 브라우저 메모리에서 짧게 재사용하는 정책을 정한다.
   학생 등록/수정/삭제·시험 배정/상태 변경·로그아웃 때의 즉시 무효화와 재인증을 함께 설계해야 한다.

개인 정보를 공용 서버 캐시에 넣거나 전역 `staleTimes`만 올려 신선도·권한 검사를 생략하지 않는다.
`staleTimes`는 현재 공식 문서에서도 실험 설정으로 분류한다. 이번 작업은 진단만이며 이러한 정책은 바꾸지 않았다.
