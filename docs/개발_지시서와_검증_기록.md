# 개발 지시서와 검증 기록

기준 v1.1 · APP-20260905-06 · 2026-09-06. 앱 기능을 개발하기 **전에** 읽는 절차 기준이다.
실제 파일 연결은 [기능 지도](../architecture/기능_소유권.json), 책임 배치는
[코드 길찾기](코드_길찾기_및_변경영향.md)가 기준이다. 상태·우선순위는 루트 작업 대장 한 곳에만 둔다.
이 문서는 배포 승인이나 DB 변경 승인이 아니다.

## 1. 시작부터 완료까지

1. 기존 기능 보완 / 새 기능 / 기존 작업 대체 / 우선순위 변경으로 분류한다. 독립 결과가 달라지면
   작업을 분리하고 대장 변경 전후를 확인받는다. 같은 기능의 작은 오류는 기존 지시서 이력에 추가한다.
2. 기존 합의, 현재 브랜치·변경 파일, 가까운 AGENTS, 기능·흐름 지도를 확인한다. 설치 버전은
   package.json과 lockfile로 확인하고 해당 버전에서 제공하는 공식 문서·설정을 대조한다.
3. [기능 지시서 양식](양식/기능_작업지시서.md)에 요구 R번호, 완료 조건, 데이터 소유자, 권한,
   요청·응답, 생성·배정·응시·조회·검색·수정·삭제·기록 흐름과 기존 연결을 적는다. 해당 없는 흐름에도 이유를 적는다.
4. 사용자 결정이 **하나라도 남으면 해당 기능 전체 구현을 멈춘다.** 조사·설계 검토만 가능하다.
   불확실한 부분만 제외하고 나머지를 구현하거나 임시 기본값을 넣지 않는다. 권장안·대안·영향을 모아
   플랜 모드에서 확인한다. 플랜 모드를 사용할 수 없으면 질문을 모아 보고하고 구현을 보류한다.
5. 기존 합의는 재질문하지 않는다. 업무 동작·자료 보존/삭제·공개·비용·배포에 영향 없는 내부 분리는
   에이전트가 대안과 이유를 기록하고 결정한다. 자체 검토는 사용자 승인이나 구현 완료가 아니다.
6. 결정 D번호, 설계 영향, 검사 T번호를 앱 내부 v1 기록에 연결하고 설계 관문을 통과한 뒤 구현한다.
   데이터·API·기능 검사마다 예상 상태, 표시 위치·공용 부품, 실제 쉬운 문구, 보존·복구 동작을 함께 정한다.
   이것은 원요구 4번의 필수 범위이며 별도 추가 요구로 취급하지 않는다.
   새 결정이 생기면 해당 기능을 다시 보류한다. 기준을 바꿀 때도 같은 절차다.
7. 코드·검사를 함께 작성하고 로컬 단위/구조/타입/lint/빌드 → 필요한 실제 화면 확인 →
   [검증 기록](양식/검증_기록.md) → 완료 관문 순서로 진행한다. 실패·미실행을 완료로 숨기지 않는다.
8. 완료와 배포는 별도다. 문서·검사 도구만 바뀌면 화면 검사는 해당 없음 사유를 기록한다.
   UI, 라우팅, 포커스, 실제 음성·네트워크 타이밍 변화는 코드 검사만으로 실화면 검증 완료를 선언하지 않는다.

## 3. 실패와 복구 표시

### 원자료 보존 검사 (APP-20260909-01)

기존 사전·교재에 있는 값이 수집/전달 단계에서 빠진 것을 정상 미등록으로 취급하지 않는다.
발음처럼 기존 값이 있는 항목은 사용자 지정/확정 승인→정확 사전→제공 원문 순서를 실제 자료 작성 계약에 연결한다.
해당 값이 있는데 null이나 자동 생성값으로 대체되면 로컬 검사를 실패시킨다. 가져오기 완료/음원 존재/해시 일치를 내용 품질 완료로 대신하지 않는다.
원본 값·출처/품사·원본 해시→전달 필드→등록 자료→실제 공통 조회→과거 및 신규 소비자까지 대조한다.
파생 자료 오류와 사전 원본 변경은 별도 판정하며, 사용자에게 사전 오염 여부를 묻는 질문에는 사전 실물과 이전 기록을 직접 비교해 답한다.

### 3.1 상태를 판정하는 기준

빈 값이라는 이유만으로 실패·0건·404를 결정하지 않는다. 입력과 응답의 의미, 현재 요청의 성공 여부를 먼저 확인한다.

- **미입력/미선택**: 아직 고르지 않은 상태다. 필수값이면 해당 입력 옆에 무엇을 고를지 안내하고,
  선택값이면 오류로 취급하지 않는다. 빈 검색어가 전체 조회인지도 기능 계약에 적는다.
- **정상 빈 결과**: 현재 사용자·검색어·필터·페이지에 해당하는 최신 유효 요청이 성공하고 응답 형식도 정상일 때만 0건으로 표시한다.
  최초 미조회, 필수 응답 누락, 잘못된 응답 형식, 통신 실패를 `[]`, `0`, `없음`, `검토 중`으로 바꾸지 않는다.
  선택 필드의 정상 null은 그 항목만 `없음` 또는 정해진 빈 안내로 표시하고 조회 실패와 구분한다.
- **조회 실패**: 새 검색이 실패하면 이전 0건을 새 검색의 결과로 보여주지 않는다. 실패 안내와 새 조건의
  `조건에 맞는 내역이 없습니다`를 함께 표시하지 않는다. 이전 자료를 유지하면 이전 결과임을 분명히 하고,
  사용자·권한이 바뀐 개인 자료는 유지하지 않는다.
- **없는 페이지/대상(404)**: 잘못된 주소 또는 권한 정책상 조회 가능한 특정 대상이 없음을 확인한 경우다.
  목록 0건이나 일시적인 서버/통신 실패와 구분한다. 권한 거절을 숨김 404로 처리하는 기존 보안 정책은 보존하고
  대상 존재 여부를 새로 노출하지 않는다. 그 정책이 미결정이면 사용자에게 확인한다.

| 상황 | 표시 위치·부품 | 보존/복구·필수 검사 |
|---|---|---|
| 초기 조회 대기 | 경로 loading.tsx / 영역 RouteLoadingState·기존 skeleton | 실제 요청만 대기. 레이아웃 유지·키보드 접근 |
| 갱신 중 | 해당 목록의 기존 표시·진행 상태 | 안전한 이전 내용 유지, 늦은 응답의 덮어쓰기/요청 취소 검사 |
| 미입력/미선택 | 입력 부근 FieldHelp, 제출 검증 실패는 FieldError | 선택 항목의 빈 값은 오류 아님. 필수값 안내와 정상 조회 0건 구분 |
| 조회 성공·빈 결과 | 해당 영역 EmptyState | 미선택·자료 없음·검색 결과 없음·지원 안 됨 구분. 0건은 현재 조건의 성공 응답에서만 |
| 입력 오류 | FieldError, 입력 부근 | 입력 보존·연결된 설명·focus. toast만 띄우지 않음 |
| 조회 실패 | PanelLoadFailure 또는 기존 영역 오류 패턴 | 실패한 영역 다시 시도. 오류를 빈 결과/0/검토 중으로 바꾸지 않음 |
| 저장 실패 | 폼의 안전한 오류·재시도 안내 | 입력 보존. 중복 제출 방지·멱등키·타임아웃 뒤 결과 확인. 무조건 자동 재전송 금지 |
| 인증/권한 실패 | 인증 안내·권한 거절 화면 | 개인 자료 즉시 숨김. 재인증/사용자 전환에서 이전 자료 재노출 금지 |
| 없는 페이지/대상(404) | 가장 가까운 not-found.tsx와 공용 빈 대상 안내 | `페이지를 찾을 수 없습니다`와 실제 이동 가능한 처음/목록 버튼. 직접 주소·모달 진입·새로고침 검사 |
| 예상 밖 예외 | 적절한 error.tsx 또는 좁은 오류 경계 | 안전한 안내+오류 식별번호. 서버 기록에 원인 연결, SQL/토큰/스택/개인정보를 화면에 노출하지 않음 |

### 3.2 쉬운 한국어 문구와 책임 분리

1. 사용자가 **무엇이 안 됐는지와 다음에 무엇을 할 수 있는지** 알 수 있게 짧고 구체적으로 쓴다.
   `값이 비어 있습니다` 대신 `시험 범위를 선택해 주세요`, `Failed to fetch` 대신
   `시험 내역을 불러오지 못했습니다. 다시 시도해 주세요`처럼 기능 이름과 행동을 적는다.
2. 개발 용어, 영어 오류 원문, 내부 코드·SQL·스택을 안내 문장으로 그대로 출력하지 않는다.
   서버/통신의 실패 종류는 기능 계약으로 구분하고, 화면 표현 경계에서 검토된 문구로 연결한다.
   알 수 없는 오류에도 안전한 기본 안내를 제공하며 `error.message`를 무조건 노출하지 않는다.
3. 확인하지 못한 원인을 단정하지 않는다. 통신 실패만으로 `인터넷이 끊겼습니다`라거나,
   저장 응답 시간 초과만으로 `자료는 변경되지 않았습니다`라고 쓰지 않는다.
   저장 여부를 모르면 `저장 결과를 확인하지 못했습니다. 목록에서 먼저 확인해 주세요`처럼
   실제로 가능한 확인 경로를 제공하고 중복 제출을 막는다.
4. 같은 의미의 문구는 [한국어 문구 카탈로그](../src/content/ko/README.md), 같은 상태·접근성의 부품은
   공용 UI를 재사용한다. 기능별 실패 판정은 계약·상태 처리에, 단순 표시는 UI에 둔다.
   로딩·빈 결과·실패를 하나의 불명확한 boolean이나 화면별 하드코딩으로 합치지 않는다.
5. 오류번호는 실제 진단 기록과 연결된 안전한 식별값만 보조로 표시한다. 식별값을 만들 수 없어도
   쉬운 안내와 복구 행동은 표시한다. 개인 자료·비밀키·정답을 문구·접근성 이름·브라우저 로그에 남기지 않는다.

### 3.3 Next.js 경계와 공용 UI 선택

경로 첫 대기는 `loading.tsx`, 독립 영역의 대기는 `Suspense`의 대체 화면으로 나눈다.
조회 실패를 로딩 화면에 무기한 남기거나, `loading.tsx`만 있으면 오류도 처리된다고 가정하지 않는다.
예상 가능한 실패는 명시적인 결과 계약으로 처리하고 예상 밖 예외만 적절한 오류 경계로 보낸다.
오류 경계가 이벤트 처리기나 모든 비동기 실패를 자동 처리한다고 가정하지 않는다.
`error.tsx`는 해당 경로의 하위 예외를 담당하고 같은 경로의 layout 예외는 상위 경계가 담당한다.
루트 layout 예외는 자체 html/body를 갖춘 `global-error.tsx`에서 처리한다. `notFound()`는
가장 가까운 `not-found.tsx`로 연결하며 일반 오류로 삼키지 않는다. API 실패 응답과 화면 404는 별도로 검증한다.
병렬 모달 슬롯의 `default.tsx`에서 의도적으로 아무것도 표시하지 않는 경우는 누락된 404와 구분한다.

Next 16.2.12 지원 범위와 다음 공식 문서를 대조했다(2026-09-06):
[오류 처리](https://nextjs.org/docs/app/getting-started/error-handling),
[로딩](https://nextjs.org/docs/app/api-reference/file-conventions/loading),
[없는 페이지](https://nextjs.org/docs/app/api-reference/file-conventions/not-found).
기존 부품 위치: [로딩·조회 실패](../src/design-system/patterns/route-state/route-state.tsx),
[빈 결과·일반 안내](../src/design-system/patterns/feedback/feedback.tsx),
[입력 오류](../src/design-system/primitives/form/field.tsx),
[404 경로](../src/app/not-found.tsx), [루트 예외](../src/app/global-error.tsx),

오류 식별번호의 실제 제공 여부는 해당 기능에서 검사하며, 이 문서 추가만으로 모든 화면 적용을 주장하지 않는다.

### 3.4 요구·화면·검사를 잇는 필수 기록

작업의 각 R번호에 대해 `발생 조건 → 응답/상태 → 위치·부품 → 실제 안내 문구 → 보존·복구 → T번호`를 적는다.
부품 이름이나 `오류 표시 확인`이라는 한 줄만으로 대체하지 않는다. 작은 UI 수정도 기존 상태의 문구·복구를
유지하는 검사를 적고, 문서·내부 도구처럼 화면이 전혀 없는 작업만 영향표에 이유를 적어 제외한다.

기능별 T번호에 다음 사례를 연결한다. 해당 없는 사례에는 이유와 기존 계약 근거를 기록한다.

- 필수 미선택 / 선택값 빈 입력 / 정상 응답 0건 / 정상 선택 필드 null / 필수 응답 필드 누락을 구분한다.
- 첫 조회 실패 / 성공 후 갱신 실패 / 이전 0건 뒤 검색 변경 실패 / 재시도 성공 / 취소와 늦은 응답을 확인한다.
- 알 수 없는 주소 / 조회 가능한 대상 없음 / 모달 직접 접근·새로고침 / 인증·권한 실패를 구분한다.
- 저장 실패·결과 불명확·중복 제출에서 입력 보존과 실제 복구 행동을 확인한다.
- 실제 렌더된 쉬운 문구·버튼·표시 위치와 금지 문구 부재를 검사한다. 오류와 잘못된 `없음`이 동시에 나타나면 실패다.
- 알림의 status/alert·입력 설명 연결·키보드·focus 및 로딩 종료를 확인한다. 내부정보·정답 노출 검사를 함께 연결한다.

자동검사는 상태·발생 조건·문구·복구·부품·T번호와 `error-ui`/`ui-copy` 검사 주제의 **누락**을 잡는다.
문구의 쉬움·정확성이나 상태 판정의 타당성은 해당 기능의 실행 검사와 사람/독립 리뷰로 확인한다.
문서·가상 예시 검사 통과를 실제 화면 검사 통과로 표현하지 않는다.

## 4. 작업 기록 형식 v1

실제 기록: `architecture/work-records/records/<작업번호>.json`.
정확한 필드·열거값 기준은 [schema.mjs](../scripts/work-records/schema.mjs)이며 모든 객체는 알 수 없는 필드를 거절한다.
앱 밖 작업 대장·개인 파일·비밀정보는 기록에 복사하지 않는다. 문서의 R/D/T 번호와 JSON 번호를 같게 쓴다.

| 묶음 | 필수 의미 |
|---|---|
| schemaVersion/id/title/size/gate/guide/baseline | 형식 1, 작업 번호, 작은 수정/전체 설계, 기록 성숙도, 앱 안 지시서, 조사 기준 커밋. gate는 대장 상태가 아님 |
| owners/plannedOwners/plannedFlows/scope | 실제 지도 소유자·흐름과 변경/확인 경로. 기존/예정/삭제를 구분하고 영향 흐름을 모두 연결 |
| requirements | R번호·요구 출처·완료 조건·소유자·흐름·T번호. 제외는 이유와 해결된 D번호 필수; 사용자 요구 제외는 사용자 결정만 가능 |
| decisions | D번호·사용자/내부 결정·미결/확정·질문·답변·출처. 재질문할 필요 없는 기존 합의도 출처 연결 |
| dataClasses/impacts/policies | 자료 성격과 모든 영향 판단·이유. 개인 자료에는 권한/자료 노출, 평가 비밀에는 정답 노출, 캐시 영향에는 캐시 검사 필수 |
| design/uiStates/standards | 자료·재사용·캐시·호환·복구 설계, 화면 상태별 발생 조건(trigger)·실제 문구(message)·동작(behavior)·복구(recovery)·부품·T번호, 기준 상태·버전·출처 |
| checks/verification | T번호·검사 파일/종류·사례·예상 결과·주제. 실제 환경·실행시각·명령·결과와 코드 해시는 실행 후 기록 |

`size:small`도 보안/상태 영향을 생략하지 않는다. 사람용 양식은 축약하되 JSON은 같은 형식이다.
화면 상태에는 `unselected`(미선택), `not-found`(없는 페이지/대상)도 포함한다. 같은 종류의 변형(전체 0건/검색 0건 등)은
trigger/message/behavior에 조건별로 적고 연결된 T에서 각각 검사한다. `message`에는 실제 문구를 쓰며,
재사용 문구는 키와 최종 표시 예를 함께 적는다. `recovery`에는 버튼 이름·이동 대상·입력 보존을 적는다.
새 문구가 없는 유지/대기 상태도 그 이유와 접근성 안내를 적는다. 내부 형식은 아직 배포하지 않은 v1을 보완했으며,
현재 실제 기록과 가상 예시를 함께 맞췄다. 과거 검증 JSON은 역사 기록으로 보존하고 새 기준의 통과로 재사용하지 않는다.
새 기능 설계의 예정 소유자·흐름·파일은 설계에서만 허용한다. 완료 때 예정 항목을 제거하고 실제 지도와
파일 연결로 전환해야 한다. 검사 결과는 `pass / fail / skipped / not_run`; 필수 검사는 pass만 인정한다.

### 세 관문과 명령 (앱 저장소에서 실행)

```text
npm run verify:work-records -- --phase format
npm run verify:work-records -- --phase design --work APP-작업번호
npm run verify:work-records -- --phase design --changed
npm run verify:work-records -- --phase fingerprint --work APP-작업번호
npm run verify:work-records -- --phase complete --work APP-작업번호
```

- 형식: 필수 항목·중복·상태/버전·기록 내부 참조와 문서 링크. 미검증 기록은 기존 경로·지도 참조도 확인.
  과거 verified 기록은 당시 경로를 보존하고 현재 일치는 완료 관문에서 재확인한다. Git을 호출하지 않는다.
- 설계: 미결정 0, 완료 조건/설계/검사 연결, 실제 또는 명시된 예정 경로. 변경 연결은 기존 변경 영향
  분석을 재사용하여 기록 없는 구현 변경·잘못된 소유자·누락된 영향 흐름을 거절한다.
- 완료: 지정 작업의 필수 검사 실제 통과, 실제 경로·소유·흐름, 당시 검사 입력과 현재 입력의 일치.
  모든 과거 기록의 완료를 매번 재판정하지 않는다.

`fingerprint`는 파일을 쓰거나 검사를 실행하지 않고 현재 입력의 해시 묶음만 출력한다. 이 출력에 실제
실행 결과를 연결한다. 해시가 달라지면 해당 검사 묶음을 다시 실행한다. 검사기는 명령 문자열을 실행하지 않는다.
해시는 scope·검사 대상·해당 소유자의 코드/테스트·연결 흐름의 의존 경로·설정에서 계산한다.
package/lock·Next/타입/검사 설정과 기능 지도도 포함한다. 인증 proxy 같은 루트 실행 파일도 제외하지 않는다.
v1 텍스트 해시는 Windows/CI의 CRLF를 LF로 정규화한 SHA-256이며 다른 공백은 바꾸지 않는다.
이미지·폰트 같은 이진 자산은 바이트 그대로 비교한다. 화면 상태에 연결한 재사용 부품도 입력에 포함한다.
지문용 자료에서 **verification와 gate, 기록 JSON 파일 자체**는 제외하므로 결과 설명을 보완해도 순환하지 않는다.
다만 요구/설계/검사 계획이 바뀌면 지문이 달라진다. 비밀 환경 파일·실제 학생 자료는 읽거나 해시하지 않는다.
실제 기록 폴더의 JSON은 제외하지만 검사가 읽는 가상 예시 JSON은 테스트 입력이므로 해시에 포함한다.

Git 변경 추적 시작점은 도입 전 `bc48313bc53840a44ab6505a8238eaabf7667eae`다. 그 이후 커밋·작업 트리·
stage·미추적 파일을 함께 확인한다. 예전 작업 전체를 소급 작성하지 않는다. 이전 verified 기록은 변경 파일의
동일 해시가 확인될 때만 당시 변경을 설명할 수 있다. 다시 바꾼 파일에는 새 유효 설계가 필요하다.
후속 작업에서 옛 파일 하나가 삭제돼도 과거 기록의 다른 동일 파일까지 다시 작성하지 않는다.
이 경우 과거 설계·입력 지문과 필수 검사 통과를 보존하고 대상 파일의 현재 소유·흐름·해시만 대조한다.
CI는 이 기준 커밋까지 이력을 받아야 하며, 얕은 clone에서 기준이 없다고 HEAD로 대체하거나 검사를 생략하지 않는다.

`verify:architecture:static`에 로컬/CI 설계·변경 검사를 연결했다. `prebuild`에는 기존 지도 검사와 형식
검사만 연결한다. 호스팅 빌드는 앱 저장소 내부 파일만 사용하며 Git·루트 대장을 요구하지 않는다.
아직 끝나지 않은 빌드의 완료 결과를 prebuild에 요구하지 않는다.
기존 `.codex-tmp`는 Git에서도 제외된 임시 시안 구역이므로 lint/타입 검사에서 제외한다.
실제 src·scripts·설정은 계속 검사하며 임시 시안 파일을 지우거나 앱 코드 오류를 숨기지 않는다.

테스트를 실행하지 않고 해시만 새로 발급해 통과했다고 기록하는 행위는 금지한다.
