# 관리자 삭제·취소 기능 검증 및 배포 대기

- 기록일: 2026-07-31
- 작업 브랜치: `codex/admin-deletion-controls`
- 상태: 코드·로컬 DB·반응형 검증 완료, 운영 DB·운영 앱 미반영

## 구현 결과

- 학생 삭제
  - 학생 코드 제거, 활성 세션 폐기, 일반 목록·새 배정 대상 제외
  - 미응시 배정은 취소하고 오답 대기는 보존
  - 진행 중 응시는 `expired/completed`로 종결해 고아 상태를 남기지 않음
  - 성적·문항·오답 원본은 보존하고 과거 내역 이름은 `삭제됨`으로 표시
- 시험 관리
  - 시험별 관리 목록에서 `시험 전체 삭제`
  - 학생별 이력에서 미응시 `배정 취소`
  - Overview·학생 관리·시험 관리 공통 이력에서 전체 시험 삭제와 개별 내역 삭제
  - 진행 중 응시가 있는 시험은 전체 삭제 거부
- 내역 삭제
  - 원본 시험·성적·오답은 보존
  - 관리자 이력에서 선택한 수신자 또는 응시 행만 숨김
  - 내역을 숨기는 순간 응시가 시작된 경우 `409`로 거부하고 새로고침 안내
- 반응형·색상
  - 학생 화면 `완료`, `새 시험`, `미응시 마감`, 마감 카운트다운 줄바꿈 방지
  - 시험 관리의 배정 버튼 글자를 흰색으로 유지
  - 학생 관리 상태 배지 색상을 후순위 선택자가 덮지 않도록 수정
- 장기 조회
  - 배정·응시·숨김 이력을 각각 1,000건 단위로 전체 페이지 조회

## DB 안전장치

- 학생·시험은 soft delete만 허용하고 물리 `DELETE`는 트리거로 차단
- 삭제된 학생·시험의 수정, 새 배정 연결, 새 응시 생성 차단
- 학생 → 시험 순서의 부모 행 잠금으로 삭제·응시 시작 경합 방어
- 취소된 수신자 행도 이력 보호 트리거로 물리 삭제 차단
- 공개 RPC는 활성 관리자만 실행하고 명시적 권한과 RLS 적용
- 활동이 한 건이라도 생기면 롤백 스크립트가 중단되도록 보호

## 중단 사유

운영 마이그레이션 안전 심사가 추가 명시 승인을 요구해 DB 적용을 중단했다.
운영 데이터와 운영 배포에는 변경이 없다. 코드만 배포하면 신규 열이 없어
관리자 페이지 조회가 실패하므로 DB 승인 전에는 `main` 병합과 Vercel 운영
배포를 하지 않는다.

## 다음 시작점

1. 사용자에게 운영 DB의 additive 마이그레이션 적용 승인을 받는다.
2. `admin_deletion_controls` 한 건만 Supabase에 적용한다.
3. 적용 직후 위 운영 스냅샷 수치가 그대로인지, 신규 열·RPC·RLS가 있는지
   확인한다.
4. Supabase security·performance advisor를 확인한다.
5. 브랜치를 `main`에 병합·푸시하고 Vercel `READY`를 확인한다.
6. 가짜 학생으로 학생 삭제·미응시 배정 취소·시험 전체 삭제·내역 숨김을
   확인한 뒤 생성한 테스트 데이터를 정리한다.
