# 코드 길찾기와 변경 영향 확인

이 문서는 앱에서 기능 하나를 고칠 때 관련 파일을 빠뜨리지 않기 위한 첫 진입점이다. 사람이든
에이전트든 파일 검색부터 시작하지 말고, 먼저 아래 순서로 기능 소유권과 연결 범위를 확인한다.

## 1. 작업 시작 순서

1. 루트 작업대장에서 현재 활성 작업을 확인한다.
2. `architecture/기능_소유권.json`에서 기능 ID와 현재 경로를 찾는다.
3. `npm run map:feature -- <기능 ID>`로 소유 경로·진입점·관련 실행 흐름을 확인한다.
4. 공용 기반을 바꾸면 `npm run map:owner -- <소유 범주 ID>`로 정확한 파일·디렉터리를 출력한다.
5. `npm run map:flow -- <실행 흐름 ID>`로 UI부터 DB·검사까지 실제 연결을 출력한다.
6. 수정할 파일에 가장 가까운 `AGENTS.md`를 읽는다.
7. 아래 변경 영향표의 각 줄을 `변경 / 확인만 / 해당 없음` 중 하나로 표시한다.
8. 코드와 검사를 함께 바꾼다.
9. 새 디렉터리·진입점·서버 파일·DB 함수가 생기면 소유권 JSON과 가까운 `AGENTS.md`도 갱신한다.
10. `npm run map:changed`와 `npm run verify:architecture`로 실제 변경 파일과 지도가 맞는지 확인한다.

소유권 지도는 “매번 모든 계층을 수정하라”는 뜻이 아니다. 모든 계층을 확인하고, 바꾸지 않은 계층은
왜 안전한지 남기라는 뜻이다. UI만 바뀌는 작업이라도 같은 규칙을 server나 DB가 별도로 계산하는지
확인해야 한다.

## 2. 변경 영향표

기능을 수정하기 전에 작업 기록이나 커밋 설명에 다음 표를 만든다.

| 확인 면 | 대표 위치 | 결과 | 근거 |
|---|---|---|---|
| 경로·Server Component | `src/app/**/page.tsx`, `layout.tsx` | 변경/확인만/해당 없음 | |
| 화면 UI | `src/features/<기능>/ui` | | |
| 브라우저 상태 | `controller` | | |
| 순수 계산·검증 | `domain` | | |
| 사용 사례 흐름 | `application` | | |
| 요청·응답 변환 | `api`, `transport` | | |
| Route Handler·Action | `src/app/api`, 기능의 `actions` | | |
| 서버 조회·변경 | 기능의 `server`, 현재 임시 `src/lib/services` | | |
| DB 스키마·RPC·권한 | `supabase/migrations` | | |
| 캐시·갱신 | React 요청 캐시, 공용 자료 태그 | | |
| 로딩·오류·Streaming | `loading.tsx`, `error.tsx`, `Suspense` 경계 | | |
| 자동검사·Preview | 가까운 테스트, 구조 검사, 브라우저 검증 | | |

검토하지 않은 빈 줄이 있으면 구현 완료로 보지 않는다. `해당 없음`도 이유를 한 줄 적는다.

## 3. 디렉터리별 책임

### 현재와 목표를 구분하는 법

- `architecture/기능_소유권.json`의 `structureState.current`는 지금 실행 중인 위치다.
- `structureState.target`은 R3~R7에서 옮길 목표다. 목표 폴더가 문서에 있다는 이유로 구현이 끝난 것으로
  보거나, 현재 호출자를 남긴 채 파일만 복제하지 않는다.
- 현재 `application`은 주로 브라우저의 요청 수명 흐름이다. 목표 구조에서는 이를 `client/flows`로,
  서버 사용 사례 조합은 `server/use-cases`로 이름과 실행 환경을 분리한다.
- 현재 `src/features/assignments/api`는 HTTP Route 폴더가 아니라 자료 변환층이다. 실제 HTTP 진입점은
  `src/app/api`다.

목표 feature 안에서는 다음 이름을 사용한다.

- `contracts`: 직렬화 가능한 요청·응답·화면 계약
- `client/{components,controllers,flows,transport}`: 브라우저 상호작용과 요청 수명
- `server/{components,queries,commands,use-cases,actions,http}`: 서버 화면·조회·명령·조합
- `ui`: hook 없는 표시 부품과 그 기능이 소유하는 CSS
- `public-ui.ts`, `public-contracts.ts`: 다른 기능에 의도적으로 공개하는 진입점

`server/http`는 실제 URL을 가진 Route Handler가 아니다. `src/app/api/**/route.ts`가 인증·상태 코드를
처리한 뒤 호출하는 서버용 요청·응답 변환기다. Server와 Client를 같은 barrel 파일에서 내보내지 않는다.

| 현재 디렉터리 | 담당 | 두면 안 되는 것 |
|---|---|---|
| `src/app` | URL, 인증 진입, Server Component 화면 조합, `loading/error`, Route Handler | 업무 계산 복사, Client 입력 상태, 직접 DB 규칙 |
| `src/features/<기능>/ui` | 글자·배치·접근성·사용자 입력 표시 | `fetch`, API 주소, DB 호출, 회차·점수 업무 계산 |
| `src/features/<기능>/controller` | 브라우저 입력 상태, 탭, focus, 요청 수명 | Supabase, server service, 핵심 검증 복사 |
| `src/features/<기능>/domain` | 날짜·범위·점수·상태 전이 같은 순수 계산 | React, JSX, 브라우저 전역, 네트워크 |
| `src/features/<기능>/application` | 미리보기·저장·충돌 복구 같은 사용 사례 순서 | 화면 마크업, API 주소, DB client |
| `src/features/<기능>/api` | 요청·응답 자료 변환과 HTTP 계약 | 실제 네트워크 실행, UI, DB 호출 |
| `src/features/<기능>/transport` | 브라우저의 HTTP 실행 한계 | 업무 계산, UI 표시 결정 |
| `src/features/<기능>/presentation` | 화면용 짧은 문구·표시 자료 변환 | DB 조회, 브라우저 상태, 저장 명령 |
| `src/features/<기능>/server/queries` | 기능 전용 읽기와 최소 화면 자료 | 숨은 쓰기, Client import |
| `src/features/<기능>/server/commands` | 기능 전용 저장·취소·거래 조합 | React, UI 문구, 읽기 이름의 숨은 쓰기 |
| `src/design-system/primitives` | 버튼·입력·탭·대화상자 같은 가장 작은 공용 UI | 기능 용어, API, feature import |
| `src/design-system/patterns` | 둘 이상의 기능이 같은 의미로 쓰는 화면 패턴 | 특정 기능의 업무 계산·DB 자료 |
| `src/components` | 앱 shell·navigation과 아직 옮기지 않은 공용/예전 부품 | 새 기능 전용 대형 컴포넌트 |
| `src/content` | 화면 문구와 번역 자료 | 업무 계산, DB 접근 |
| `src/styles` | 전역 token·theme·reset | 특정 기능 전용 화면 규칙 |
| `src/test-support` | 여러 기능이 공유하는 검사 도구와 fixture | 운영 진입점, 실제 개인정보 fixture |
| `src/lib/admin` | 여러 서버 경계가 공유하는 순수 관리자 계약·정책 | React, 네트워크 실행, DB client |
| `src/lib/services` | 현재 남아 있는 서버 서비스와 진짜 기능 공통 조합 | 새 기능 전용 서비스의 무기한 추가 |
| `src/lib/quiz` | 배정·응시·결과가 함께 쓰는 순수 문항·발음·단어 계산 | React, 네트워크, DB client, 화면별 상태 |
| `src/lib/assignment` | 배정 Preview·저장이 함께 쓰는 순수 문항 계획 | React, 화면 상태, DB client |
| `src/lib/auth`, `src/lib/supabase` | 인증·권한, DB client 생성 | 화면 표현과 기능별 계산 |
| `src/lib/database` | DB 계약 검사와 migration 검증 도구 | 화면 코드 |
| `src/lib/observability` | 서버 오류 식별과 기록 | 기능별 업무 계산, Client 비밀 노출 |
| `src/lib/deploy` | 배포 환경 계약 검사 | 런타임 화면 코드 |
| `src/lib/ui` | 기능에 종속되지 않은 표시 계산과 경로 | DB 접근, 기능별 저장 규칙 |
| `src/lib/vocab` | 단어 자료 투입 계약 | 학생별 학습 상태, 화면 코드 |
| `supabase/migrations` | 스키마, RPC, trigger, 권한, 거래 불변식 | 화면용 문구·Client 상태 |

목표 위치와 현재 위치가 다르면 `architecture/기능_소유권.json`의 현재 경로를 먼저 확인한다. 기존
`src/lib/services` 파일을 한꺼번에 옮기지 않고 R3~R6에서 호출자와 검사를 먼저 전환한다. 새 기능 전용
서버 코드는 원칙적으로 `src/features/<기능>/server/queries|commands`에 둔다.

## 4. 기능 소유권

| 기능 폴더 | 주 책임 |
|---|---|
| `src/features/assignments` | 단어 시험 단일·일괄·오답 배정, 수정, 일정 미리보기 |
| `src/features/assignment-queue` | 완료 뒤 다음 시험을 만드는 이어지는 배정 상태와 조작 |
| `src/features/students` | 관리자 학생 목록·선택 상세·학생 설정 |
| `src/features/history` | 관리자 개요·내역·수정 진입 화면 |
| `src/features/student-dashboard` | 학생의 현재 시험과 완료 내역 첫 화면 |
| `src/features/quiz-player` | 학생 시험 진행과 답안 상호작용 |
| `src/features/results` | 학생 시험 결과 화면 |
| `src/features/learning-points` | 포인트 표시 자료와 공용 표시 부품 |
| `src/features/session` | 학생 세션 갱신 화면 경계 |
| `src/features/notifications` | 알림 요청 계약 |

시험 수정처럼 둘 이상의 feature가 만나는 기능은 임의로 한 폴더만 보지 않는다. 정확한 파일 목록은
소유권 JSON 한 곳만 기준으로 삼고, 가까운 `AGENTS.md`는 그 폴더의 책임과 빠뜨리기 쉬운 연결만 설명한다.

공용 기반은 `map:feature`가 아니라 `map:owner`로 찾는다. 현재 공용 소유 ID는 `app-shell`, `auth`,
`shared-contract`, `shared-ui`, `shared-admin-command`, `shared-quiz-domain`, `shared-infra`,
`database-contract`, `architecture-meta`다. 예를 들어 인증·Supabase 기반은
`npm run map:owner -- shared-infra`, 공용 UI는 `npm run map:owner -- shared-ui`로 확인한다.

배정 영역은 업무 흐름 6개와 공통 작업공간 흐름 2개로 나뉜다. `assignment-workspace-load`가 서버의
초기 자료 준비를, `assignment-workspace-selection`이 브라우저의 학생 찾기·선택을 맡는다.
범위·요일·오답·이어지는 배정 흐름은 선택 흐름을 선행 흐름으로 참조하고, 선택 흐름은 초기 자료 흐름을
참조한다.
내역 상세에서 시작하는 수정 흐름은 별도 Server Component 경계를 사용하므로 이 공통 흐름에 의존하지 않는다.
흐름 선행 관계에 순환이 생기면 구조 검사가 실패한다.

### 기능 지도 검사기의 책임

- `scripts/check-feature-map.mjs`: 전체 등록부와 Next.js 진입점·migration 보호를 검증하는 명령 진입점
- `scripts/feature-map/common.mjs`: 경로·파일 목록·해시 공통 처리
- `scripts/feature-map/import-graph.mjs`: TypeScript import와 직접·간접 기능 의존 분석
- `scripts/feature-map/runtime-flow.mjs`: 실행 시 사용하는 import만 따라 UI→상태→서버→계약·계산 경로를 닫음
- `scripts/feature-map/flow-verification.mjs`: 흐름의 필수 면·진입점·실제 import·예외 근거를 검증
- `scripts/feature-map/change-impact.mjs`: 흐름 그래프를 한 번 계산해 현재 Git 변경 영향에 재사용
- `scripts/feature-map/owner-output.mjs`: 기능·공용 소유 범주의 길찾기 출력
- `scripts/feature-map/ownership-catalog.mjs`: 검사·변경 영향·소유자 출력이 함께 쓰는 정확한 소유 목록

`import type`과 `typeof import()`는 실행 경로에 넣지 않는다. 같은 파일 안의 다른 탭·상세 분기처럼 실제
사용자 행동에서 실행하지 않는 import는 이유가 적힌 정확한 간선 예외로만 제외한다. 자동 추적된 소스와
같은 이름의 가까운 테스트도 흐름 검사에 포함된다.

`page.tsx`, Route Handler, Next.js 특수 진입점뿐 아니라 루트 `next.config.*`와 `src/app`의
`layout/loading/error/not-found`, 경로별 CSS·폰트·계약 검사도 정확한 소유 목록으로 보호한다.
`npm run build`의 `prebuild`가 전체 소유권 지도를 검사하므로 등록되지 않은 새 경로는 Preview 배포 전에
실패한다. `map:changed`는 Git 비교 기준이 필요한 사람·CI용 영향 확인이며, Vercel 빌드의 완전한 현재 트리
검사는 `verify:feature-map`이 맡는다.
삭제·이동 경로는 현재 지도에서 사라졌더라도 `HEAD` 또는 비교 기준 커밋의 이전 지도에서 소유자와 선언된
실행 흐름을 복원한다. 상세 흐름 소유 파일을 흐름 설명 없이 지우거나 옮기면 변경 영향 검사가 실패한다.

## 5. Next.js 기능을 놓는 위치

### Server Component와 Client Component

- `page.tsx`는 권한을 확인하고 서버 query를 시작해 화면 조각을 조합한다.
- 상호작용이 없는 제목·집계·첫 목록은 Server Component로 유지한다.
- 탭·토글·입력·focus처럼 브라우저 상태가 필요한 가장 작은 경계만 Client Component로 만든다.
- 큰 controller 객체 전체를 하위 UI에 전달하지 않고 필요한 값과 callback만 전달한다.

### Streaming과 오류 경계

- 화면 shell, 집계, 목록, 선택 상세가 서로 독립적으로 느릴 때만 별도 `Suspense` 경계를 둔다.
- 인증과 권한 확인 전에 개인 자료를 stream하지 않는다.
- `loading.tsx`는 경로 전체 뼈대, 패널 skeleton은 독립 query 경계가 소유한다.
- 시험 플레이어는 일부 문제만 먼저 보이지 않도록 완전한 시험 상태를 하나의 경계로 유지한다.

### 캐시

- 같은 RSC 렌더 안의 인증·공용 자료 중복만 React `cache()`로 줄인다.
- 학생, 배정, 응시, 오답, 점수, queue, 알림은 요청 사이 공용 캐시에 넣지 않는다.
- `use cache`, `cacheLife`, `cacheTag`는 R8의 공용 단어장·범위·분류 전용 경로에서만 사용한다.
- 앱 내부 저장 성공은 관련 태그의 즉시 갱신, 외부 자료 반영은 보호된 경로의 느슨한 갱신을 사용한다.
- 캐시 키를 만들기 위해 학생 ID·토큰·개인 조건을 공용 캐시 함수에 넘기지 않는다.

### 해시와 멱등키

- 화면 변경 여부 해시는 `domain/api`의 정규화된 업무 의미를 사용한다.
- DB 멱등키는 `server/command`와 migration이 최종 기준이며 Client 성공 결과를 장기 캐시하지 않는다.
- 캐시 태그, 화면 변경 fingerprint, DB 멱등 요청 hash를 같은 용도로 재사용하지 않는다.

## 6. 공용 UI로 올리는 기준

- 한 기능에서만 쓰는 단어 시험 UI는 그 feature의 `ui`에 둔다.
- 둘 이상의 기능이 같은 의미·상태·접근성 규칙으로 반복해서 쓰면 `design-system/patterns` 후보로 올린다.
- 모양만 비슷하고 업무 의미가 다른 부품을 억지로 합치지 않는다.
- 공용 부품은 feature, service, API 주소를 import하지 않는다.
- 공용화할 때 기존 사용처를 한 번에 바꾸지 않고 대표 소비자→회귀 검사→나머지 소비자 순서로 옮긴다.

## 7. 완료 조건

- 기능 ID와 모든 현재 경로가 소유권 JSON에 있다.
- 기능 흐름의 최종 소유자·참여 기능·개인/공용/변경 자료 성격·캐시·점진 표시 정책이 기록돼 있다.
- 변경 영향표의 모든 줄에 결과와 근거가 있다.
- 가장 가까운 `AGENTS.md`의 금지 의존 방향을 지킨다.
- 화면 계산과 server/DB 계산이 같은 domain 계약을 사용한다.
- 새 경로와 guide 링크가 구조 검사에서 실제로 존재한다.
- 관련 단위·계약·통합 검사가 통과한다.
- `npm run map:changed`에 지도 밖의 기능 코드가 없고 기존 기능 간 직접 import나
  `기능 → lib → 다른 기능` 간접 의존이 늘지 않는다.
- `map:changed`는 작업 트리와 고정된 도입 기준 커밋 이후 변경을 함께 검사한다. CI에서는 명시한
  기준 브랜치나 이전 배포 SHA가 있으면 그것을 우선 사용한다.
- 기준 시각 이후 migration, 공용 component, 공유 시험 계산, 기능 server 파일은 전수 소유권 목록과
  일치한다. migration 기준 시각은 검사기에 고정되어 임의로 앞으로 옮길 수 없다.
- 각 기능 흐름에 적힌 경로의 실제 소유 기능이 최종 소유자 또는 참여 기능 목록에 포함돼 있다.
- 실행 경로 자동 추적 결과와 `해당 없음` 선언이 충돌하지 않고, 선행 흐름 그래프에 순환이 없다.
- 흐름의 핵심 직접 import 간선은 실제 코드와 일치하고, 인증·Supabase·DB 계약·관측·배포·공용 표시·
  단어 투입 디렉터리의 파일 경로 묶음은 등록된 수와 해시가 일치한다.
- DB·배포가 포함되면 Preview 한 건 적용, readback, 복구 방법, 브라우저 확인을 기록한다.
- Production과 실제 학생 변경은 별도 명시 승인 없이는 하지 않는다.
