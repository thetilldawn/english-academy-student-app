APP-20261002-04 / M06. 2026-10-03. 사용자 승인 D12/D13을 구현하고 로컬 및 검토용 DB 검증을 마쳤다. 운영 DB 반영·실제 오래된 기록의 최초 정리·자동 일정 활성화·용량 회수·앱 배포는 별도 단계다.

## 결과

성공한 예약 실행 상세는 종료 후7일, 실패는30일, 사용 불가 세션은7일, 로그인 실패는24시간 뒤 정리할 수 있다. 미시작 준비는 확정 만료 후24시간, 구형 중복 본문은 종료·전체 복원 확인 후24시간을 적용한다. 기존 새 참조 형식, 실제 응시·답·결과·오답·포인트·기기 미접수 답과 공용 단어 내용은 정리 대상에서 제외한다.

준비를 정리해도 작은 만료 확인을 남긴다. 같은 준비/자율연습 요청을 재전송했을 때 새 시험을 만들지 않고 만료를 알린다. 이미 시작한 시험은 원래 시험 번호·시작 시각·문항을 그대로 복원한다.

운영 담당자용 미리보기와 제한량 실행을 분리했다. 기본250·최대1,000행, 고정 기준시각·정책 확인값·다음 위치·반복 요청 확인을 사용한다. 잠긴 기록은 건너뛰고 다시 확인할 대상으로 남긴다. 짧은 실행 예산은 반복 처리의 예산이며 DB 조회 자체의 절대2초 완료 보장은 아니다.

## 발견해서 고친 문제

1. 번호를 앞0/대문자로 다르게 적으면 보존 대상이 빠질 수 있어 정규화했다.
2. 첫 후보를 처리하기 전 예산이 끝나면 같은0건 결과를 반복할 수 있어 최소 한 후보에서 진행하도록 했다.
3. 실제 Supabase는 cron.job에 SELECT만 허용한다. 첫 SQL의 행 SHARE 잠금은42501로 실패했다. 후속 SQL은 정리할 상세만 잠그고 각 DELETE 시작 시 보이는 확정된 현재 작업·과거 실행·허용 목록·기간·보존 표시·행 확인값을 모두 다시 대조한다. 권한을 확대하거나 운영 일정을 바꾸지 않았다.
4. 위 재대조에 READ COMMITTED를 강제했다. 작업 변경으로 실제 DELETE가0건이면 삭제 성공 수를 늘리지 않고 제외/재순회로 기록한다.

후속 DELETE 도중 확정된 cron 설정 변경은 다음 DELETE부터 보인다. 설정 변경 자체를 막는 잠금과 같은 보장을 주장하지 않는다. 첫 상세 삭제 뒤 같은 거래의 가짜 트리거가 명령을 바꾸는 검사는 후속 재대조 회귀이며, 원격 두 연결의 cron 설정 변경 검사는 아니다.

처음의 전체 검사7파일 실패는 가상 cron 구조에 실제 열이 빠진 문제였고 수정 후 재검사했다. HTTP 통신 차단·요청이 순차로 실행된 시도·가짜 세션의 코드 세대 불일치는 검사 준비 실패로 분리했다. 가짜 보존 요청의 private 오류는 P0002였으며, 임시 HTTP 도구가 다른 오류번호를 예상해500으로 전달한 것은 없는 대상 거절/보존0으로 검증했다. 이 임시 도구는 제거했고 앱 공개 경로가 아니다. 실패한 시도를 성공 근거에 합치지 않았다.
