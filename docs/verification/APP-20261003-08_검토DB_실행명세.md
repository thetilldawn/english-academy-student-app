# 제출 확인 기록의 검토 DB 적용·검사 명세

대상은 격리 검토 DB `wojxpruvbjzbhrpmsbuy`다. 운영 `xdxhswjgksukjmpbzqgz`에는 적용하지 않는다. 사용자 승인 유지보수 및 APP08 D9의 작은 가짜 검증에 한정한다.

## 적용과 보존

- 파일 `supabase/migrations/20261003233000_compact_local_quiz_receipt_responses.sql` 하나만 적용한다. 파일 해시·원격 이력·함수 본문은 결과에 연결한다.
- 새 내부 함수 3개와 기존 제출 함수의 반환·저장 두 지점만 바꾼다. 기존 표·행·색인·RLS·불변 트리거·시간 열은 변경하지 않는다.
- 인증·기기 연결·학생/응시 잠금·동일 제출 충돌 검사는 기존 코드다. 내부 함수는 빈 search_path와 SECURITY INVOKER, 앱 3역할 실행 금지를 유지한다.
- 기존 15개 관련 표의 행 수와 정렬한 행 확인값, 제출 함수 OID/소유자/ACL/설정을 적용 직전·직후 대조한다. 가짜 검사 뒤에도 가짜 학생/응시/문항에서 파생한 행만 제외하고 같은 확인값을 비교한다.
- 기존 원형 접수 19행은 모두 같은 응답으로 읽어지는지 검사한다. 이 숫자는 적용 전 실측이며 학생 수나 앱 이용 가능 인원이 아니다.

## 작은 실제 두 연결 검사

별도 가짜 관리자1명·학생2명·자료4단어·배정3개를 사용한다. 처음 두 연결의 네트워크 승인 지연으로 대기가 성립하지 않아 첫 학생의 이미 끝난 가짜 시험은 유지하고 새 배정1개를 추가했다. 식별자 접두 `a9080000-0000-4000-8000-`, 자료 키 `receipt-preview-a908`, 학생 메모 `APP08-a908: 실제 학생 아님`을 대조한다. 실제 학생·기존 자료는 쓰기 대상으로 선택하지 않는다. 두 연결을 준비한 뒤 가짜 관리자 표시명에 한시적 준비 표식을 넣어 순서를 맞추고, 종료 전에 원래 표시명으로 복원한다.

1. 동일 요청: SQL 연결이 신규 제출 결과를 저장한 거래를 잡고, 별도 HTTP 연결이 같은 요청으로 기다리는 것을 서버의 서로 다른 PID와 Lock 대기로 확인한다. 앞 거래 확정 뒤 두 응답이 정확히 같고 답/포인트가 한 번만 늘어야 한다.
2. 같은 제출 ID·다른 답: 같은 방법으로 대기를 확인한 뒤 뒤 요청은 충돌로 거절한다. 앞 요청의 결과·답·접수만 남아야 한다.
3. 성공한 최초 접수의 축약 저장·원응답 복원·앱 규격 검사와 권한9개를 확인한다. 필요하면 내부 조회의 실행 계획을 따로 수집한다. 함수 호출 EXPLAIN만으로 내부 조회를 검증했다고 주장하지 않는다.
4. 가짜 학생과 배정을 기존 종료 함수로 닫고 가짜 자료·관리자를 비활성화한다. 학생 답과 접수의 불변 보호를 검사 편의상 끄지 않는다. 별도 공개 검사 함수를 만들지 않는다.

## 실패·복구

적용 단계는 하나의 거래이며 예상 원함수의 변경 지점이 달라지면 중단한다. 신규 접수는 축약 전·저장 직후 원응답 확인값이 일치해야 하며 실패 시 답/결과/오답/포인트와 함께 취소한다. 이미 축약 저장이 생긴 뒤에는 새 형식을 모르는 옛 제출 함수로 단순 복원하지 않는다. 신규 저장을 원형으로 돌려도 원형/축약형의 읽기는 모두 유지해야 한다. 기존 접수 삭제나 운영 용량 회수는 이 명세에 없다.

## 한계

전체 접수표를 세는 조회는 제거했다. 고정 계획의 최대500문항과 각 문항·접수의 기본키 조건, 전체 응답 SHA를 대조한다. 계획 밖에서 직접 위조된 무관한 행을 찾아내는 전역 무결성 감사는 별개다. 작은 검토 DB의 응답 시간은 운영 동시 접속 인원이나 대규모 성능 보장이 아니다.
