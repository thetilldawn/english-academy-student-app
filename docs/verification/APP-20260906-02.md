## 최종 판정 — R5 보완 후

범위 표시 입력을 좁히고, 배정 전용 확인창에서 기존 공용 대화상자 부품과 한국어 문구 모음을 재사용했다.
취소·Escape·상단 닫기는 입력을 유지하며 ‘버리고 닫기’만 기존 닫기를 호출한다. 확인 중 제출과 저장 중 폐기를 차단한다.

- 전체 378파일 **2,199개**, 관련 2파일 32개, 타입·lint·구조/변경 연결·요청 캐시(calls=2)·환경 검사·격리 새 Next 빌드 통과.
- 독립 리뷰의 중복 클릭 검사 보완 후 해당 22개와 타입·lint를 재실행했다. 같은 갱신 묶음에서 두 클릭→닫기 1회·저장 0회다. 재리뷰 추가 지적 없음.
- [새 실제 화면 근거](APP-20260906-02-discard-ui.json): 단일 85점/일괄 90점 보존, 첫 초점 ‘계속 작성’, 취소 후 ‘닫기’ 초점 복귀, Enter→Escape 취소와 스크롤 유지, 명시 폐기 후 창 0개 확인.
- 오답·바깥 클릭·저장 중 잠금·중복 방어는 컴포넌트 검사다. 실제 화면에서 해당 분기까지 직접 확인했다고 확대하지 않는다.
- T1~T8과 완료 관문 통과. 관련 구현·테스트·설정 **613개** 지문:
  `906c637283742680ff085e2005673f9b844ad1a246af3ad3e17f4b01f60f5c9a`.
- 실제 DB/학생 자료/업무 규칙/캐시 정책/의존성/커밋/업로드/배포는 바꾸지 않았다. 로컬 서버 exit 0, 3037/3038/3040 리스너 종료, 검사 탭 32/33만 정리했다.

이전 기본 확인창에서 키보드 입력도 시간 초과됐다. 앱/도구 원인은 확정하지 않았다.
[당시 부분 검증](APP-20260906-02-before-discard-ui.json)과 아래 이력을 보존하며 새 확인창 검증과 구분한다.

## R5 적용 전 부분 판정과 이력

0단계의 가짜 자료 기준을 확보하고 1-A 범위 표시 부품을 분리했다. 자동검사는 통과했지만,
**변경 내용을 버리는 기본 확인창의 실제 화면 검사 1건(T7)이 끝나지 않아 전체 완료로 판정하지 않는다.**
캐시 정책·일정 계산·배정 저장·학생 자료·DB·커밋·업로드·배포는 변경하지 않았다.

## 실제 변경

- 범위 표시 부품은 전체 배정 제어기 대신 선택 단어장·단원 목록·선택 순서·필요한 동작·해당 오류만 받는다.
  날짜/학생/점수/저장 상태를 이 부품에서 직접 참조하지 않는다.
- 실제 범위 배정 화면과 기존 조립 부품을 모두 새 계약으로 연결했다. 같은 단어장 찾기/범위 선택/입력 안내 부품,
  문구·스타일·버튼 참조·역순 선택을 보존했다. 전체 일정/질문 설정 제어기까지 분리한 것은 아니다.
- 독립 범위 입력 4건, 기존 조립 창의 변경 폐기 확인/취소 2건, 로컬 검사 도구 보호 21건을 추가했다.
  닫기 분기는 기존 앱 코드를 바꾸지 않고 검사만 보완했다.
- Next.js/구조 검토 기준에 따라 기존 공용 UI를 재사용하고 표시 입력을 좁혔다.
  Next 16.2.12/React 19.2.8/Node 24.19.0을 유지했으며 새 프레임워크 API나 의존성은 도입하지 않았다.

## 화면 이동 기준에서 확인한 점

| 조건 | 표본 | 표시 대기 중앙값 | 요청 관찰 |
|---|---:|---:|---|
| 학생 메뉴로 다시 이동 | 10 | 332.7ms | 두 메뉴 왕복에서 실제 RSC 20회·사전 로딩 7회 |
| 배정 메뉴로 다시 이동 | 10 | 328.9ms | 개인 목록을 다시 조회함 |
| 뒤로/앞으로 | 각 10 | 6.4 / 7.0ms | 실제 목록/API 재조회 0, 사전 로딩 17회는 별도 |
| 같은 배정창 다시 열기 | 10 | 62.5ms | 준비 조회 API 10회: 열 때마다 다시 요청 |
| 검색 입력/해제 | 20 | 295.1ms | 목록 API 20회 |
| 학생/배정 문서 다시 열기 | 각 10 | 84.1 / 86.9ms | HTTP 캐시 유지. 첫 스트리밍 화면/FCP 수치 아님 |

1. 메뉴를 새로 눌러 이동할 때와 뒤로/앞으로 갈 때의 재사용 정도가 다르다.
2. 같은 배정창을 다시 열어도 준비 자료를 매번 조회한다.
3. 학생 등록 영역이 접혀 있어도 학생 페이지 진입 시 자료 두 종류를 읽는다.

이 세 곳을 후속 최적화의 기준으로 남긴다. 이번에는 캐시를 바꾸거나 비용이 줄었다고 판정하지 않는다.
원기록에는 상위95%·HTTP/API/RSC/사전 로딩·바이트·가짜 자료 요청을 분리했다.
JS 전송 관찰값 0은 번들 크기가 0이라는 뜻이 아니다. 실제 DB·인증 지연·비용은 측정하지 않았다.

## 브라우저 한계와 보완

[분리 후 원기록](APP-20260906-02-after.json)에 성공/중단을 함께 보존했다.
단일·일괄에서 DAY 2 → DAY 1을 선택하면 “DAY 2~DAY 1 · 2개 선택”이 나타났고, 찾기 취소 후에도 유지됐다.
내용을 바꾸지 않은 배정창은 10번 모두 열고 닫혔다. 이 표본은 최초 코드 로딩도 포함하므로 변경 전 예열 표본과
성능 향상/저하를 직접 비교하지 않는다.

변경 후 닫기에서는 두 탭의 입력 호출과 후속 화면 조회가 시간 초과됐고, 확인창 조회는 빈 결과였다.
새 탭은 정상이다. 기존 `requestClose`는 변경 시 `window.confirm`을 사용하지만, 이것만으로 앱/도구 중 어느 쪽
문제인지 확정할 수 없다. 단일/일괄의 취소→입력 유지·확인→닫기 1회·저장 0회는 컴포넌트 검사로 보완했다.
입력 부품/제어기 대역을 사용하므로 실제 브라우저 확인창 표시·닫기를 통과로 바꾸지 않는다.

재개 시 이 미확인 분기부터 확인한다. 앞선 100회 기준 측정과 전체 자료 조사부터 다시 시작하지 않는다.
이후 일정 부품 분리/불필요 조회 제거/새 캐시는 기존 실행계획 순서를 따른다.

## 정리 및 복구

- 루프백 전용 가짜 계정/학생 2명/단어장 2권만 사용했다. 실제 앱에 인증 우회나 검사 Route를 넣지 않았다.
- 로컬 서버는 정상 종료(exit 0), 기존 `.next` 복구를 확인했다. 이번 검사 탭 29/30/31만 닫고 사용자 운영 탭은 보존했다.
- [예비 실행](APP-20260906-02-preliminary.json)의 오류/중단도 보존했다. Windows 종료 확인이 거절된 첫 실행은
  기존 빌드를 자동 덮어쓰지 않았고, 이 도구의 하위 작업만 확인해 종료한 뒤 복구했다.
- 임시 빌드와 원기록은 재검토용으로 보존했다. 사용자 자료/원본 삭제는 없다.
