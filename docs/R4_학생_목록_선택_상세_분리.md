# R4 학생 목록과 선택 상세 분리

## 1. 결론

R3와 R3-S의 Next.js 경계는 되돌리지 않는다. R4도 같은 기준을 사용한다.

- 첫 학생 목록은 Server Component가 서버 query를 직접 호출한다.
- 검색·필터·다음 10명처럼 브라우저 상호작용만 Route Handler를 거친다.
- 학생 상세는 학생 ID 경로로 지연 렌더하고, 목록 배열에서 상세 자료를 찾지 않는다.
- 보호 layout과 각 서버 query가 관리자 인증을 확인한 뒤에만 개인 자료를 읽고 표시한다.
- 학생·이력·오답·포인트는 요청 사이의 공용 캐시에 넣지 않는다.
- 목록, 상세, 오답, 배정 큐의 수명과 커서를 서로 섞지 않는다.

구현 전 첫 화면은 전체 학생·전체 이력·전체 오답 요약·전체 포인트를 하나의 Client 작업공간에 넘겼다.
현재 R4 구현은 이 묶음을 목적별 읽기 모델과 요청 수명이 분리된 상호작용 경계로 교체했다.

## 2. 범위 모순 정리

기존 R4 완료 조건의 `선택 바구니`와 `필터 결과 전체 선택`은 학생 관리 화면의 기능이 아니다.
사용자가 확정한 기준대로 단어 배정은 단어 시험 관리에서만 시작한다.

- R4: 학생 관리 목록과 선택한 학생 상세를 분리하고, R5가 재사용할 학생 목록 계약을 만든다.
- R5: 단어 시험 관리의 선택 바구니를 페이지와 독립시킨다. 필터 전체 선택은 서버가 전체 대상 ID를
  확정하고, 저장 직전에 기존 권한·학생 상태 검사를 다시 수행한다.

학생 관리에 배정용 체크박스나 선택 바구니를 다시 추가하지 않는다.

## 3. 화면과 Next.js 경계

### 첫 진입

`/admin/students`는 보호 layout의 인증 뒤 다음 두 Server Component 읽기를 형제 `Suspense` 경계에서
병렬 시작한다. 각 query도 DB 접근 직전에 `requireAdmin()`을 다시 실행한다.

1. 학생 첫 페이지 10건+다음 행, 결과 수, 필터 선택지
2. 학생 추가 폼에 필요한 선택 가능한 단어장 목록

첫 학생 목록은 Server Component가 query를 직접 부른다. 앱의 Route Handler를 서버에서 다시 HTTP로
호출하지 않는다. 목록 영역에는 실제 카드 높이와 맞는 `Suspense` skeleton을 둔다.

### 검색·필터·더보기

검색, 학교, 학년, 계정 상태, 수업그룹, 단어장, 오답 조건을 정규화해 전용 Route Handler에 보낸다.
처음 조건과 다음 페이지는 같은 DB 정렬·필터 계약을 사용한다. Client controller는 요청 취소, 현재 조건,
표시 중인 페이지와 오류만 맡고 업무 분류를 다시 계산하지 않는다.

### 학생 상세

목록 행은 `/admin/students/[studentId]` 링크다.

- 같은 앱 안에서 클릭: parallel/intercepted route가 모달을 렌더한다.
- 새로고침·직접 주소: 같은 자료 계약으로 전체 상세 페이지를 렌더한다.
- 선택 학생이 현재 10명에 없어도 학생 ID로 독립 조회한다.

직접 주소와 가로채기 모달은 모두 `StudentDetailRouteContent`와 같은 상세 query를 공유한다. 서버가
상세 자료와 첫 이력 10건+다음 행을 읽고, 직접 페이지·가로채기 모달의 표시 껍데기와 프로필 편집·
코드/접근·탭·이력 필터/더보기·오답 조작은 공용 Client 상세 영역을 사용한다. 내역 패널은 Client
영역의 `next/dynamic`으로 실제 탭 방문 전 다운로드도 늦춘다. 목록 링크는 `prefetch={false}`이며,
목록 첫 응답에는 상세 자료가 들어가지 않는다.

## 4. 읽기 모델

### 학생 목록

`get_admin_student_directory_initial_v1`

- 같은 SQL 시점의 `snapshotAt`, 필터 결과 수, 필터 선택지, 최대 11행을 반환한다.
- 화면에는 10행만 보내고 11번째 행으로 다음 커서를 만든다.
- 행은 이름·학교·학년·상태·코드 상태·현재 단어장·최근 시험 시각·완료/미응시/응시 전 개수와 현재
  포인트를 포함한다.
- 포인트는 원장의 현재 합계표를 page 학생에 묶음 join하고 `rawPoints`로 보존한다. 화면에서만 최소
  0으로 표시한다.

`list_admin_student_directory_page_v1`

- 첫 조회의 `snapshotAt`, 같은 필터 지문, 불투명 커서를 사용해 최대 11행만 반환한다.
- 정렬은 `최근 학습 또는 생성 시각 DESC, studentId ASC`다. 커서에는 두 값을 모두 넣는다.
- OFFSET을 사용하지 않는다.

### 선택 학생 상세

`get_admin_student_detail_initial_v1`

- 학생 ID 한 건의 프로필·코드 상태·현재 포인트·활성 학습 출처
- 시험 이력 최신 10건+다음 행과 전체 개수
- 현재 오답 요약
- 자료별 최근 학습·응시 횟수를 DB에서 집계한 단어장 이력

`list_admin_student_history_page_v1`

- 상세 첫 조회의 snapshot과 `effectiveAt DESC, entryKey ASC` 복합 커서를 사용한다.
- 다음 10건+다음 행만 반환한다.

`snapshotAt`은 목록 정렬과 이력 페이지 경계를 고정하는 기준이다. 이후 수정된 프로필을 과거 값으로
되돌려 읽는 시점 조회는 아니다.

오답 단어 전체는 오답 탭을 실제로 연 현재 학생 한 명의 상세 경로 생명주기 안에서만 재사용한다.
배정된 시험 큐는 기존 20건+1 복합 커서를 유지한다. 상세 shell, 오답, 큐를 한 응답으로 합치지 않는다.

## 5. DB와 보안

- 공개 함수는 `SECURITY INVOKER`, `STABLE`, 빈 `search_path`를 사용한다.
- 함수 안에서 활성 관리자 여부를 다시 확인한다.
- `PUBLIC`, `anon`, `service_role` 직접 실행은 막고 관리자 세션의 `authenticated`만 허용한다.
- 기존 R3 관리자 이력 분류를 호출하거나 같은 계약을 재사용해 목록과 상세의 상태 분류가 갈라지지 않게
  한다.
- 인덱스는 예상으로 추가하지 않는다. Preview `EXPLAIN (ANALYZE, BUFFERS)`에서 실제 병목이 확인된
  경우에만 별도 migration으로 추가한다.
- Preview 현재 규모는 학생 29명, 학생 배정 124건, 응시 41건, 오답 사건 464건이다. 이 수치는 기능
  검증 표본이며 조회 상한으로 사용하지 않는다.

## 6. 코드 소유 경계

```text
src/features/students/
  contracts/       목록·상세의 직렬화 요청/응답 계약
  controller/      목록 요청 수명, 프로필, 코드·접근, 탭, 이력, 오답 상태
  transport/       목록·이력의 브라우저 후속 HTTP
  api/             변경 요청과 기존 오답 후속 요청
  server/
    components/    첫 목록과 상세의 Server 조합
    queries/       목록·상세·이력 페이지의 인증·DB 읽기
    *-cursor.ts    불투명 커서의 생성·검증
  domain/          오답 선택 등 표시와 무관한 순수 규칙
  ui/              목록·생성·상세 조합
    panels/        정보·계정·오답·시험 이력 패널
```

절대 줄 수 제한은 두지 않는다. 파일은 목록, 프로필, 코드·접근, 오답, 화면 전환처럼 변경 이유가 다른
책임을 기준으로 나눈다. Server와 Client를 같은 barrel에서 내보내지 않으며, UI에서 `fetch`, DB 조회,
포인트 합산을 수행하지 않는다.

기능 흐름 `student-management-screen`은 R4 읽기 수명과 같은 화면에서 사용하는 학생 생성·프로필·접근·
오답 변경과 관리자 공용 이탈 보호 접점을 함께 추적한다. R4 완료 범위는 목록·상세 읽기 모델 분리다.
학생 변경 전체는 `map:feature -- students`, 공용 이탈 보호는 `map:owner -- app-shell`, 로그아웃 요청은
`map:feature -- session`으로 확인한다.

관리자 shell의 내부 링크는 app-shell 소유 `GuardedLink`가 Next.js `Link.onNavigate`로 등록된 이탈
요청을 받는다. 학생 상세와 내역의 배정 수정은 `useRouteExitGuard`에 dirty·busy 상태만 등록한다.
저장 중에는 확인창 없이 이탈을 막고, 변경 내용이 있을 때만 한 번 확인한다. 새로고침·탭 닫기는
`beforeunload`, 모달 닫기는 `requestExit`, 저장 성공·학생 삭제는 `forceExit`을 사용한다.

로그아웃처럼 먼저 성공해야 하는 비동기 명령은 결과 Promise를 보호 기능에 그대로 반환한다. 실패하면
원래 화면의 base/sentinel 보호 기록을 복구하고, 성공한 경우에만 로그인 화면으로 이동한다. 다른 화면으로
이미 바뀐 뒤 실패한 명령은 옛 편집기의 보호 기록을 새 화면에 다시 만들지 않는다.

평상시 관리자 링크는 Next.js Client 이동을 그대로 사용한다. 다만 변경 내용을 버리고 이동하겠다고 승인한
경우에는 문서 단위 이동을 사용한다. parallel/intercepted route가 이전 편집 화면을 뒤에 계속 마운트해
초안과 이탈 가드를 남기는 경우를 막기 위한 예외이며, 저장 중이거나 이동을 취소한 경우에는 실행하지 않는다.

## 7. 변경 영향표

| 확인 면 | R4 처리 |
|---|---|
| 경로·Server Component | 학생 첫 목록, 직접 상세, intercepted 상세 경로 변경 |
| 화면 UI | 기존 카드 의미는 유지하고 page/empty/loading 표시만 분리 |
| 브라우저 상태 | 목록, 상세 전환, 프로필, 코드·접근, 이력, 오답 캐시 controller 분리 |
| 순수 계산 | 필터 정규화·커서 지문만 이동, 시험 상태 규칙은 기존 공용 계약 재사용 |
| 요청·응답 | 목록·상세·이력 page 계약 추가 |
| Route Handler | 브라우저 목록 후속 읽기와 상세 이력 후속 읽기만 추가 |
| 서버 조회 | 전체 묶음 loader 제거, 목적형 query 추가 |
| DB | Preview 전용 신규 함수만 추가, 기존 함수 삭제·교체 없음 |
| 캐시 | 개인 자료 `private, no-store`; 공용 단어장 캐시는 R8 전까지 기존 요청 중복 제거만 사용 |
| Streaming | 인증 뒤 목록 skeleton, 상세 route 자체 loading 경계 |
| 자동검사 | 커서·필터·10→10→나머지·선택하지 않은 상세 0회·DB/화면 대조 |

## 8. 검증 기준

- 학생 0·1·10·11·21명과 최근 학습 시각이 같은 학생 여러 명
- 검색·학교·학년·상태·수업그룹·단어장·오답 조건 및 빈 결과
- 필터 변경 중 이전 요청 취소와 느린 이전 응답 무시
- 학생 추가·수정·삭제 뒤 현재 필터와 표시 깊이를 보존한 목록 재조회
- 삭제 직전 필터·더보기 응답이 늦게 와도 삭제 카드가 되살아나지 않는지
- 필터 실패 시 실제 적용 조건으로 되돌아가고 더보기를 다시 시도할 수 있는지
- 첫 화면 payload에 전체 이력·전체 오답·전체 학생 ID가 없는지
- 상세를 열지 않았을 때 상세/오답/큐 query 0회
- 현재 10명 밖 학생의 직접 상세 주소와 intercepted 모달이 같은 자료를 표시하는지
- 이력 21건을 10→10→1로 읽고 중복·누락이 없는지
- 포인트 DB 음수 보존과 목록/상세의 화면 최소 0 표시, 관리자 시험 상세의 부호 보존
- 함수 권한, 새 보안·성능 advisor, Preview 실행 계획과 응답 크기
- 직접 상세와 가로채기 상세에서 뒤로가기 취소·승인, Forward 잔여 기록, 여러 단계 뒤로가기
- 로그아웃 실패 뒤 입력 유지·보호 복구·두 번째 로그아웃 성공
- Production·실제 학생 변경 0건

App Router에는 브라우저의 여러 단계 `popstate`를 취소하는 공개 API가 없다. 단위검사는 다른 Next
history state를 보호 주소로 복사하지 않는 것까지 보장한다. 여러 단계 뒤로가기 취소의 실제 복구는
Preview의 실제 브라우저 검사 전까지 완료로 처리하지 않는다.

## 9. 현재 검증 체크포인트

- 전체 335파일·1,790테스트, lint·typecheck·기능 지도·구조 4파일·64테스트 통과
- Next.js 16.2.12 Preview 설정 build 통과, 학생 목록과 직접·가로채기 상세는 요청 시 서버 렌더
- 내역 패널 동적 청크 35,141바이트가 상세 첫 client-reference manifest에서 제외됨
- Preview migration `20260829030759`, 관리자/비관리자 권한 격리와 학생 29명 11→11→9 검산 완료
- 목록·이력 API의 성공·401·403·400·409·503 비공개 응답 실행 검사와 미저장 승인 후 문서 이동 검사 통과
- 로컬 migration `20260829213000`과 MCP로 적용한 Preview 원격 이력 `20260829030759`를 같은 변경으로
  연결해 기록하며 일괄 `db push`는 사용하지 않음
- 커밋·자동 Preview 배포와 실제 브라우저의 직접/가로채기 상세·여러 단계 뒤로가기 검증 전이므로
  R4 상태는 `in_progress`를 유지한다.
