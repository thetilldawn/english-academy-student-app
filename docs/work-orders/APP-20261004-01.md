# 단어장 검색 지연 수리

M10 실제 검토에서 이름 검색마다 22~23초를 기다렸다. 원인은 최신 판의 큰 fixed_composition에서 includedKeys를 범위별로 다시 꺼내는 SQL이다. 최대 16,148,136B·123범위의 원형 함수 10,678.296ms를 131.845ms로 줄이는 읽기 전용 후보에서 3,003자 검색 문자열 SHA가 같았다. 아직 앱 전체 통과나 운영 반영은 아니다.

R1/T1·T3: 필요한 작은 키 배열을 한 번 꺼낸다. R2/T1·T2·T3: 포함 범위의 연도·월·타입·학년, 메타데이터, 최신 판, 빈 결과, 구형 종류/권한/커서를 유지한다. R3/T1·T3: 내부 함수 한 개 본문만 교체하며 기존 행·나머지 함수·OID/ACL/소유자/설정을 보존한다.

D1은 기존 유지보수의 같은 오류 보완이다. D2는 MATERIALIZED CTE에서 최신 recipe/includedKeys만 한 번 추출한다. D3은 새로운 캐시/검색 자료/학생 저장을 만들지 않는다. D4는 로컬 검사→검토 원형 대조→같은 SQL 검토 적용→실제 화면 순서이며 운영 반영은 M10의 별도 검증 뒤다.

변경: DB 검색 본문과 회귀 검사/안내. 확인만: API 계약·서버 권한·목록 요약·검색 표시·종류 필터·커서. 해당 없음: 새 UI/라우팅/문구/캐시/음원/학생 답 저장. 로딩/없음/오류 표시는 기존대로 유지하며 성능 감소는 실제 브라우저 시간으로 검사한다.

검사: T1 원함수 대조 및 최신 판/일부 제외/빈 키/반복 범위/낡은 판/알 수 없는 분류·대소문자/문자열 기호·함수 메타와 모든 기존 자료 보존. T2 기존 조건·종류·권한 회귀/타입/lint/지도/설계. T3 독립 검토, 전체 활성 단어장 문자열 hash, Preview 동일 SQL 보존, 실제 저장/검색/분류/삭제. 가짜 데이터만 사용하며 실제 학생 쓰기0.

복구는 보관한 이전 함수 본문만 가능하다. 학생/단어장 행은 되돌리지 않는다. 상태와 순서는 루트 대장만 따른다.
