## 현재 코드와 실제 DB에서 확인한 점

- 학교 검색은 공식 응답으로 `교육청:학교코드`를 이미 만든다. 그러나 `use-school-search`의 선택 동작은 이름만 보관한다. 응답에는 학교급이 없고 학생 DB에는 school_name/grade_label 문자열만 있다.
- 운영 DB 정보구조를 읽기 전용 조회했다. 학교/달력/평가 일정에 해당하는 테이블과 학교 일정 RPC는 없다. 기존 학생 행을 조회하거나 수정하지 않았다. 이번 단계에서는 별도 학생 정보/성적 원본을 파일로 내보내지 않았다.
- 기존 배정 학년 비교는 중1/고1 등 학교급이 포함된 저장값을 사용한다. 화면 선택지를 1·2·3으로 바꾸어도 저장값에서 학교급을 잃으면 안 된다.
- 프로필 저장 중 새 입력은 보존하고 충돌 시 기준값·버전만 갱신하는 처리는 올바르다. 성공 안내는 새 입력을 반영하지 않아 저장 후 재편집 및 저장 중 추가 입력에 잘못 남는다.
- 결과 확인은 읽기 요청인데 정보 패널의 저장 버튼은 busy만 보고 ‘저장 중’을 표시한다. checking을 먼저 구분해야 한다.
- 결과 불명 복구 버튼은 feedback 안에 있다. 입력 시 모든 안내를 지우면 복구 버튼도 사라질 수 있어 needsCheck/인증/충돌 상태를 성공 안내와 구별한다.
- 개요의 기존 내역은 앱 단어시험 내역이다. recentExamAt도 학교 시험 날짜가 아니다. 학교 일정 실패가 기존 내역까지 가리지 않도록 별도 조회·표시 경계를 둔다.

## 데이터와 조회 설계

학교 공통 자료는 검토된 로컬 운영정보에서 가져오며 앱 Git에 원문이나 실제 학생 자료를 넣지 않는다. 학교 식별자는 공인 교육청·학교코드로 연결한다. 신규 학교 선택 키와 이름은 한 저장 동작으로 처리하고, 직접 입력으로 학교 이름이 달라지면 이전 키가 남지 않게 한다. 기존 이름만 있는 학생의 학교를 문자열 유사도나 부분 일치로 자동 확정하지 않는다.

학교 공통 일정·출처·버전을 보존할 공간과 학생의 학교 선택 키를 분리한다. 독립 검토의 최소안은 비공개 스키마에 학교 일정 버전 묶음 테이블 1개와 students의 nullable 학교 선택 키 1개를 추가하는 것이다. 일정 묶음에는 학교키·학년도·학기·자료 버전·SHA-256·현재본 여부와 검증된 JSON을 저장한다. 같은 학교·연도·학기에 현재본은 하나만 허용하며 이전 버전은 보존한다. 별도 전국 학교 관리 기능은 만들지 않는다. 학생 프로필 버전 검사를 우회하거나 이전 저장 RPC에서 옛 학교 키가 남게 하지 않는다.

원문 자료의 학교ID와 앱 학교키를 각각 보관한다. 기존 학생의 키를 학교명만으로 자동 채우지 않는다. 기존 학생 연결은 학교코드가 확인된 선택을 프로필 버전 검사로 저장하는 기존 사용자 동작에 붙인다. 기존 값의 일괄 변경이나 학생 정보 자동 보정은 이번 범위가 아니다. 현재 학생에게 즉시 일정을 보이려면 기존 학생의 학교 연결 확인도 필요하며, 운영 반영 전에 이 조건을 확인한다.

관리자 첫 화면은 서버 조회, 후속 필요 갱신만 API를 사용한다. 같은 학교 학생 수만큼 반복 조회하지 않고 학교·학년 단위로 묶는다. 개요는 기존 내역과 독립적으로 실패를 처리할 수 있는 일정 집계 경계를 우선한다. 목록은 현재 페이지 학생들에 대한 일괄 요약 조회로 조합하고 다음 페이지도 동일 계약을 사용한다. 새 일정 조회 실패를 기존 단어시험 내역/학생 목록의 실패로 확대하지 않는다. 학생 화면은 `requireStudentSession()`에서 얻은 현재 학생 ID만 서버로 전달한다. 학생 브라우저에서 임의 학생 ID·학교 ID로 다른 학생 소속을 조회하지 않는다. Supabase 사용자 JWT와 앱의 자체 학생 코드 세션을 혼용하지 않는다.

새 DB 테이블은 명시적 권한과 RLS를 함께 작성한다. authenticated라는 이유만으로 전체 학생 연결 자료를 공개하지 않는다. service_role 키는 서버에만 두고 RPC 실행 권한도 좁힌다. 새 테이블의 자동 API 노출 변경과 RLS 문서를 확인했다: [공식 변경 안내](https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security).

공유 개인 캐시를 추가하지 않는다. 학교·학년 저장 성공 후 현재 학생 목록과 일정 연결을 갱신하며, 저장 결과 불명일 때는 자동 재저장하지 않는다. 기존 개인 캐시의 인증·로그아웃·학생 변경 폐기를 유지한다. 날짜 계산에는 서버에서 결정한 한국의 오늘 날짜를 명시적으로 전달하며 UTC/사용자 기기 시간대에 따라 하루 밀리지 않도록 한다.

| 상태 | 표시와 동작 |
|---|---|
| 일정 로딩 | 해당 구역에서 ‘학교 일정을 불러오고 있습니다.’ 기존 단어시험 내역은 유지 |

| 409 충돌 | 최신 기준값/버전만 반영하고 작성값 보존, 다시 검토 후 저장 |
| 인증 실패 | 기존 개인정보 숨김 범위에 학교 일정/이름도 포함하고 로그인 경로 제공 |

## 독립 검토 결과

- 학생 입력 담당은 학교 검색 결과의 키/학교급 전달, 학교명 재입력/초기화 시 선택 해제, 기존 학년 저장 형식 보존을 확인했다. 기존 모든 프로필 값을 새 열거형으로 제한하면 과거 자유입력 값을 가진 학생 수정이 막힐 수 있으므로 생성 입력의 제한과 과거 값 보존을 구분한다.
- DB 연결 담당은 신규 일정 묶음과 nullable 학교키의 최소안을 제안했다. 학교 선택은 이름+키 동시 저장, 이름만 바뀌는 구 경로는 옛 키 제거, 학생 본인 조회는 service_role 한정 현재 세션 범위가 필요하다.
- 저장/화면 담당은 성공 후 재편집, 저장 중 추가 입력, 읽기 전용 결과 확인의 잘못된 문구 3곳을 확인했다. 복구 경고를 일괄 제거하지 않고 기존 409·초안·인증·이탈 보호를 유지하는 방향이다. 화면 너비 대신 실제 카드·헤더 너비로 시험 표시를 옮길 것을 권고했다.
- 메인이 현재 코드와 운영 DB 메타데이터를 대조했다. 기존 기능지도 검사는 통과했으나 이는 새 기능 실행·브라우저 검증 결과가 아니다.
