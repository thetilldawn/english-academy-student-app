# DEPLOY-20260929-03 — 운영 단어장 조회 보완

기존 승인 기능의 배포 중 발견한 같은 조회 오류를 수정한다. 새로운 기능이나 사용자 결정은 없다. 상태·순서는 루트 대장만 따른다.

## 재현과 범위

운영 기존 테스트 학생의 내 단어장 첫 조회가 8초 뒤 실패했다. 532단어/662오답/118반복이며, 역할 제한시간은 8초다. 읽기 전용 같은 RPC에서도 57014를 재현했다. 활성 배정 비교에서 같은 출처의 단어 식별 함수를 반복 호출한다. 기존 10,001개 검사에는 활성 배정 문항이 없어 이 비용을 검사하지 못했다.

- R1: 실제 자료 규모에서도 승인된 조회가 성공해야 한다. 목록·필터·정렬·페이지·상세와 연습/교사 원천 조회의 결과 및 권한을 유지한다.
- D1: `first_occurrence`와 `first_group`의 기존 인자를 유지하여 출처별 `review_key`를 MATERIALIZED CTE에서 한 번 계산한다. 두 비교만 그 열을 사용한다. 전역/역할 제한시간을 늘리거나 빈 결과로 실패를 숨기지 않는다.
- T1: 가짜 오답 600개·활성 배정 수천행·대기 항목을 포함해 전후 전체 JSON 및 계산 공유 구조/권한을 비교한다. 실제 함수 호출 횟수를 계측한 검사는 아니다.
- T2: 기존 단어장·자율연습·교사배정 DB 회귀를 실행한다.
- T3: 실제 테스트 학생 읽기 결과 전체 동등성, 검토→운영 동일 SQL, 학생값/권한/다른 함수 보존, 8초 이내 실행을 확인한다.
- T4: 운영 테스트 학생으로 첫10개·다음10개·최근순·상세/복귀·실제 음원을 읽기 확인한다. 실제 시험 생성·배정·답안 쓰기는 금지한다.

새 migration은 함수1개 내부만 좁게 변경한다. 출력 형식·테이블·학생값·ACL·RLS는 바꾸지 않으며 기존 migration은 고치지 않는다. 공통 조회의 학생/연습/교사 소비자를 함께 검사한다. UI/경로/상태 문구 변경은 없고 기존 실패 화면은 실제 조회 성공으로 복구되어야 한다.

사전 읽기 진단: 후보 실행 계획 2,900ms, 계획305ms. 수정 전/후 한 거래의 전체 JSON은 동일(09e873b418555629b43a98b4bbbd796f)했다. 첫 비교 초안은 조회 상한을 전학생으로 놓아 불일치했고, 기존과 같은 본인 initial 상한으로 고쳐 동일함을 확인했다. 이 진단은 아직 함수 적용·최종 화면 성공을 뜻하지 않는다.

기준: [PostgreSQL WITH 계산 공유](https://www.postgresql.org/docs/current/queries-with.html#QUERIES-WITH-CTE-MATERIALIZATION), Supabase 성능 지침의 EXPLAIN ANALYZE 대조. 시간은 측정 환경의 값이지 전체 사용자 성능 보장이 아니다.
