# 불필요한 조회 제거와 요청 안 재사용

- [기록](../../architecture/work-records/records/APP-20260906-07.json), [개발 기준](../개발_지시서와_검증_기록.md), 기존 실행계획 2단계.
- R1: 닫힌 학생 등록 준비조회0 → 첫열기1 → 성공 후 재열기 추가0. 정상 빈목록과 실패를 구분하고 이름/학교/학년/메모/단어장 선택을 보존한다. 실패/조회중 직접 submit도 금지. T1/T2/T5.
- R2: 학생/배정 목록의 정규화한 동일 성공·진행중 조건은 재요청하지 않는다. 명시 재시도와 저장·삭제 후 갱신은 생략하지 않는다. 초기 단위목록 []에도 이미 조회한 단어장 ID를 연결한다. T3/T4.
- R3: 배정준비에서 이미 읽고 검증한 현재 단어장 자료를 같은 서버요청 안에서만 재사용한다. 별도 단위API와 최종 저장 검사는 그대로 최신 조회한다. T4/T5.
- R4: 기존 가짜 로컬 기준과 실제 Link 요청을 다시 비교한다. 인증 요청/목록 조회/화면 대기를 구분하며 실DB비용 감소를 측정했다고 하지 않는다. T6/T7/T8.
- D1 사용자: 구조·캐시가 먼저, 학생 단어 가리기는 마지막. 이 단계는 승인 계획의 내부 최적화다. D2/D3 내부: 기존 API/공개 경계·컴포넌트 수명 재사용, 취소후 재열기는 새조회 가능, 실패는 명시 재시도. 사용자 미결정0.
- 생성=준비조회만 변경, 배정=현재 요청 자료재사용, 조회/검색=동일조건중복제거. 응시/수정/삭제/기록의 업무명령은 변경없고 해당 성공후 최신조회는 보존한다. DB·권한정책·버전·새의존성·학생자료·업로드 변경없음.
- 로딩=실제 대기만, 오류=영역 Notice와 ‘다시 불러오기’, 정상빈자료=‘단어장 없이 학생과 코드부터 만들 수 있습니다.’, 권한거절=등록폼/코드숨김+‘로그인을 다시 확인해 주세요.’. 기존404/예상밖경계 유지. 원문SQL/영어에러를 노출하지 않는다.
- UI는 기존 표시부품, 요청수명은 준비controller, HTTP는 배정transport, 응답판정은 contracts, 교차기능은 public-client. 전체 등록폼을 재마운트해 입력을 지우지 않는다.
- 캐시: 같은 요청/같은 마운트 한정. 새 개인목록 TTL/스토리지/공유서버캐시를 이번에 넣지 않는다. 실패/취소를 성공으로 저장하지 않는다.
- T1 준비수명, T2 실제 등록/성공실패, T3 두 목록검색, T4 서버/단위빈값, T5 응답형식/권한/no-store, T6 전체·타입/lint/구조/새빌드, T7 격리 실제화면/요청량, T8 독립리뷰.
- 공식근거: [Next16.2.12 서버/브라우저 경계](https://github.com/vercel/next.js/blob/v16.2.12/docs/01-app/01-getting-started/05-server-and-client-components.mdx)는 Server자식이 Client모달 안에 있어도 미리렌더됨을 설명한다. 따라서 서버자료props를 접힌 영역에 보내는 구조만으로 지연조회되지 않는다.
- [Supabase 공식Next 인증](https://supabase.com/docs/guides/getting-started/tutorials/with-nextjs)의 getClaims/getUser 검증 및 개인응답 공유캐시 금지 원칙을 보존한다. 2026-09-06 [공식 변경기록](https://supabase.com/changelog.md)의 관련항목을 확인했고 현재조회에 적용할 DB/SDK변경 없음. 외부DB를 수정하지 않는다.
- 복구: 해당 단계만 역패치, 기존 API/DB불변. 전단계 검사기록은 당시지문으로 보존. 완료 지문/실화면·미측정분리는 검증문서에 기록.
- D4/T3 독립검토 보완: 배정 목록의 오류 안내에도 기존 첫페이지 갱신을 ‘다시 불러오기’ 버튼으로 연결하고 실제 화면 회귀에서 필터/선택 바구니 보존을 확인한다. 해당 UI는 후속분리 분류를 유지하며 의존 확대 없이 소스 지문을 갱신한다.
