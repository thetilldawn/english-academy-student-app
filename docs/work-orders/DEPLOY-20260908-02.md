# 학생·배정 개선 프리뷰 통합

## 승인 후 반영 근거

- 실제 Preview 검사 결과와 보호 근거는 [최종 검증 기록](../verification/DEPLOY-20260908-02.md)으로 연결한다. 옛 승인 대기 항목은 당시 미저장 사실이며 최신 완료 판단과 구별한다.

- D4 승인 후 Production 선택을 해제하고 `codex/local-assignment-check-20260905` 한 브랜치만 선택했다. NEIS_API_KEY는 Secret으로 저장했으며 저장 목록에서 Preview·해당 브랜치 단독을 확인했다. 키 값은 문서·Git·출력에 넣지 않았다.
- staging 지정 migration 적용 성공. 실제 함수 원본과 대조해 학교·학년 projection 두 항목만 추가됐고 소유자·권한·security invoker·빈 search_path가 같다. 원본 함수는 Git 제외 보관이다.
- 함수 SHA256 `79994ae652285d20cb9a42afb8ed475752dffe37bf748f25e4589c23084f42c6` → `b95115411d010221f9090c7a118f4a02ad9f336889b44a73aa2d556cff356aec`. 학생 저장 검사 전, migration 적용 직전·직후 보호 자료18개 영역의 수량·전체 행 해시는 동일했다. 보안96·성능78 기존 안내 중 신규0건이다. 이후 테스트학생 저장·원복에 따른 정상 수정시각과 감사 기록은 최종 검증서에서 구분한다.
- 구현은 APP02 `f9ffba1` → APP03 `4e84c31` → APP04 `1ec7b55`로 분리했다. 중간 커밋은 게시하지 않고 최종 결합 소스만 검증·Preview 게시한다. 최종 작업트리 구현 잔여 변경0, 사용자 tmp와 비밀 환경 파일 제외.

사용자의 로컬 완료 뒤 r/ㄱㄱ는 다음 Preview 통합 확인 승인이다. APP02/03/04 개선만 반영하며 main·Production·실제 학생/정답/음원/자료태그는 변경하지 않는다. 상태·순서는 루트 대장만 관리한다.

- R1: 로컬 최종 검사와 같은 코드인지 대조하고 지시서별 기록·커밋 후 기존 프리뷰 브랜치만 게시한다. 중간 분리 커밋을 각각 검증 완료로 선언하지 않는다.
- R2: 기존 Vercel 프로젝트의 Preview에만 서버용 NEIS_API_KEY를 설정한다. 운영·Development·다른 프로젝트에는 넣지 않는다. 조회 없음/실패는 직접 입력을 유지하며 값을 앱/Git/로그에 남기지 않는다.
- R3: 20260907235924_admin_history_school_labels.sql 한 개만 staging에 적용한다. 원래 함수 정의/권한/자료 집계를 보관하고 최소 학교·학년·삭제학생 null·기존 정렬/관리자 경계를 확인한다. 전체 db push나 과거 migration 재실행 금지.
- R4: Preview 테스트학생으로 상세 왕복·목록 유지·학교 저장/읽기/원복, 배정 숫자/범위/미리보기/필터/중첩 확인창을 모바일/PC에서 확인한다. 새 시험 배정/응시/점수 쓰기는 하지 않는다.

T1 현재 로컬 근거 → T2 지정 함수 → T3 프리뷰 환경/빌드 → T4 실제 화면 → T5 실학생·운영 불변. [기록 v1](../../architecture/work-records/records/DEPLOY-20260908-02.json). 새 결정이 필요한 오접속/태그 변경/운영 배포는 멈춘다.

복구는 적용 직전 실제 함수만 대상으로 한다. 테스트학생은 최신 버전으로 학교만 원복하고 정상 감사 이력을 삭제하지 않는다. Preview 코드 문제는 이전 검증 소스로 별도 전진 커밋하며 강제 push/운영 전환 금지.

## 설정 조작 승인 대기

- 기존 원격 main/Preview는 ee7be43으로 읽기 확인. staging은 ACTIVE_HEALTHY. Vercel MCP의 팀 목록은 성공하지만 프로젝트 목록0/직접 조회404였고, 기존 로그인된 앱브라우저 관리 화면에는 해당 프로젝트가 정상 표시됐다. 연결을 바꾸지 않았다.
- 새 변수 기본 선택이 Production이었다. 현재 Preview 브랜치를 선택하자 Production과 Preview가 함께 선택되어, 저장하지 않고 운영 선택을 해제하려 했다. 자동 보호가 `Environments` 하위 메뉴 진입을 모든 환경 확대라고 두 차례 거절했다. 실제 운영 체크 해제 위치에는 도달하지 못했다.
- 키 값은 아직 입력/저장하지 않았다. 미저장 창은 Close로 종료했다. 원격 DB/학생/배포/환경 변경0, Git stage/커밋/push0. 승인된 migration 독립 검사5파일23건은 통과했지만 실제 적용은 미실행이다.
- D4 승인 후에만 설정 조작을 재개한다. 운영 체크 해제→해당 Preview 브랜치 단독 여부 확인→키 입력/저장 순서이며 운영 적용 권한을 요청하는 것이 아니다.
- 이후 사용자 “반영해야지”로 D4 조작을 승인했다. 운영 기본 선택 해제와 현재 Preview 브랜치 단독 확인 후 재개한다. 앞선 미저장/거절 기록은 당시 사실로 보존한다.

공식 근거: [Vercel Git](https://vercel.com/docs/git), [환경별 변수](https://vercel.com/docs/environment-variables), [Supabase migration](https://supabase.com/docs/guides/deployment/database-migrations). 기존 Node24/PG17은 변경 안내의 Node20/PG14 종료 대상이 아니며 새 SDK·인증 방식은 도입하지 않는다.
