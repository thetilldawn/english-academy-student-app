# F01 · 운영에 반영된 패치를 앱 공지로 연결

유형: APP, 최초 요청의 별도 신규 기능. 용량 유지보수의 선행 조건은 아니다. 결정 D16이 정해진 뒤 구현한다. ‘패치하면 공지’ 요구는 확정이며, **앱 공지함+새 소식 표시를 첫 전달 방식으로 쓰는 안**은 아직 권장 설계다. 이메일/카카오톡/휴대폰 푸시까지 승인된 것으로 넓히지 않는다.

## 1. 요구와 완료 조건

| R번호 | 완료 조건 | 소유자/검사 |
|---|---|---|
| F01-R1 | 실제 운영에 반영하고 검증한 변경 묶음만 공개 | notifications+배포 운영 / F01-T1/T2 |
| F01-R2 | 코드만/SQL만/둘 다 바뀐 경우 모두 같은 발행 절차 | notifications/운영 / F01-T2 |
| F01-R3 | 이벤트 재전송·동시 공개에도 공지 한 번 | 서버/DB / F01-T3 |
| F01-R4 | 학생·관리자 대상/본인 읽음/시험 중 유예 | notifications/session/quiz-player / F01-T4/T5 |
| F01-R5 | 실패·취소·운영 되돌림·옛 화면의 사실과 안내 일치 | 배포/공지 / F01-T6/T7 |

## 2. 발행 계약

공지 단위는 ‘커밋 한 개’나 ‘배포 시도’가 아니라 **운영 변경 묶음**이다. 다음 필드를 작은 운영 기록으로 보관한다.

- 변경 묶음 ID·관련 작업 번호·대상 프로젝트/운영 환경.
- 현재 코드 커밋/실제 운영 배포 ID와 이번 코드 변경 유무. SQL만 바뀌어도 기존 운영 코드의 증거를 유지.
- SQL 파일/실행문 확인값·대상 DB·적용 결과 또는 SQL 변경 없음.
- 관련 검증 결과·실제 대표 주소/DB 연결·철회/되돌림 상태.
- 검토된 제목·학생용/관리자용 짧은 본문·대상·내용판·발행 가능 상태.
- 공개 ID·시각·중복 방지 키·정정/후속 공지 연결.

상태는 초안→문구/대상 검토 완료→적용 확인 중→공개 가능→공개로 구별한다. 적용 실패/철회는 공개하지 않는다. 문구·대상을 사전에 승인한 변경 묶음은 실제 반영/검사 조건을 충족한 뒤 자동 공개할 수 있게 한다. 원시 커밋 메시지를 그대로 학생에게 보내지 않는다.

배포 이벤트는 서명·프로젝트·운영 환경을 확인한 뒤 현재 운영 상태를 다시 조회하는 계기로만 쓴다. SQL만 반영한 패치는 승인된 적용/검사 완료 기록을 서버 절차에 등록하여 같은 최종 발행기를 호출한다. 브라우저가 임의로 ‘DB 완료’를 보내 공개할 수 없게 한다.

‘변경 없음’과 ‘증거 없음’은 다르다. 발행 직전에 실제 운영 주소의 배포 ID/커밋·연결 DB·필요 SQL 확인값이 변경 묶음과 일치하는지 다시 확인한다. SQL만 바뀌었다는 이유로 운영 코드/DB 연결 확인을 생략하지 않는다.

## 3. 화면과 읽음

권장 첫 화면: 최근 공지 한 줄+새 소식 표시, 공지함 목록/상세. 본문을 열거나 명시적 확인 버튼을 누른 시점을 읽음으로 정의하고 단순 목록 조회/기존 알림 수령 기록과 구분한다. 구체적인 읽음 동작은 D16에 함께 확정한다.

시험/자율연습 중 일반 패치 공지는 가로막지 않는다. 완료 후 또는 메인 복귀에서 표시한다. 구버전 앱이 열려 있으면 “새 기능이 반영됐습니다. 시험을 마친 뒤 새로고침해 주세요.”처럼 실제 상태에 맞게 안내하고 강제 새로고침하지 않는다.

공지 내용은 전체 검토 근거/학생 기록을 담지 않는 짧은 사용자 안내다. 서비스 공지와 학원/담당별 공지는 구조를 구분한다. 최초에는 현재 서비스의 학생/관리자 대상만 지원하며 학원별 작성/조회는 F02 권한 검증 뒤 연다.

| 기존 경로 | 구현 책임 |
|---|---|
| [알림 시작 부품](../../../src/components/notification-bootstrap.tsx) | 기존 확인 주기에 공지 개수/버전만 연결, 별도 반복 타이머 남발 금지 |
| [알림 서버](../../../src/lib/services/notification-service.ts) | 시험 알림과 공지 읽음의 의미 분리, 현재 권한 확인 |
| [학생 알림 API](../../../src/app/api/student/notifications/route.ts), [관리자 알림 API](../../../src/app/api/admin/notifications/route.ts) | 해당 대상의 요약, 본문은 상세에서 최소 조회 |
| [공지 기능 지침](../../../src/features/notifications/AGENTS.md) | 새 공지 목록/상세·읽음·발행 흐름의 실제 소유권 등록 |
| [검토 배포 검사](../../../.github/workflows/preview-smoke.yml) | 기존 Preview 성공이 운영 공지를 공개하지 않음. 별도 운영 변경 검증 연결 |

공개 기록에 변경 묶음 고유 제약을 두고 읽음은 사용자+공지판으로 저장한다. 본문 수정이 이전 읽음을 무조건 초기화할지, 중요 정정은 새 공지로 낼지는 D16에서 정한 정책을 따른다. 공개 후 되돌림은 조용한 삭제 대신 기존 공지 정정 또는 연결된 안내로 남긴다.

캐시는 공용 공개 본문/판과 개인 읽음/대상을 분리한다. 사용자 전환 시 개인 새소식 수·읽음·목록을 비운다. 게시/정정 후 관련 목록을 갱신한다. 실패한 게시 요청은 같은 변경 묶음의 결과를 먼저 확인하고 중복 공지를 만들지 않는다.

## 5. 구현 순서와 상태

1. D16 전달 방식/읽음/공지 운영자 범위 확정 → 공지/발행/읽음 계약.
2. 사용자 공지함+대상 권한+시험 중 유예 구현.
3. 운영 변경 묶음 기록과 조건 검증기 구현. 코드/SQL 독립 경로 연결.
4. 원격 이벤트의 서명·재전송·취소·최신 적용 상태 검사.
5. 검토 환경에서 전체 사례 확인 후 실제 반영 명세를 가진 패치에 연결.

변경: routing/UI/state/domain/data/API/cache/asyncUi/security/styles/tests. 기존 Field/List/Dialog·고정 화면 틀을 사용한다. 정상0건 “아직 공지가 없습니다.”, 조회 실패 “공지를 불러오지 못했습니다.”, 게시 결과 불명 “공개 결과를 확인하고 있습니다.”, 권한 실패/404/예외는 공통 U8~U10으로 구별한다.
