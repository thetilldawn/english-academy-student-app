# 검토 원자료 묶음의 파일 보관과 선택 복구

승인된 M08-A/OPS-20261003-01의 같은 유지보수 보완이다. 상태는 루트 대장만 관리한다. 원자료 묶음에는 시험에서 이미 별도 값으로 읽는 원고·검토 사본이 중복되어 있다. 이번에는 `private.reviewed_mock_source_releases_v1.bundle` 한 열만 다룬다.

## 요구·완료 조건

| 요구 | 완료 조건 | 검사 |
|---|---|---|
| R1 원자료 보존 | 실제 기존 등록기로 새 SQL 전 가짜 자료 생성, 원행 파일 저장·재읽기 확인 뒤에만 한 묶음 축소 | T1,T2 |
| R2 현재 기능 보존 | 등록 재요청 결과·승인·단어·발음·뜻·범위·판 확인값 및 모든 비대상 열 동일 | T1,T3,T5 |
| R3 제한된 실행 | 1건·크기·시간 상한, 원행 확인값·환경·동시 잠금, 중단/재요청과 늦은 등록 재조회 | T2,T4 |
| R4 선택 복구 | 지정 묶음만 원래 본문으로 복구, 이후 추가된 학생 답/기록과 다른 묶음 불변 | T5 |
| R5 권한·회귀 | 앱 역할 접근0, 직접 수정 거절, 다른 불변 보호 유지·기존 회귀·구조/타입/빌드 | T3,T6 |

## 확정 결정

- D1 사용자: 원문은 복구 가능한 파일에 보존하고 온라인에는 필요한 공용 학습값·키·태그를 남긴다. 학생 배정·완료·오답·답 보존 정책은 바꾸지 않는다. 기존 M01/M08 지시 및 계속 진행 승인이다.
- D2 사용자: 운영 정리는 M08-B의 실제 사본·정확한 대상 명세·공간 예산·복구 확인 후 실행한다. 이 단계는 도구와 가짜 자료의 검토 DB 검증이며 운영 쓰기/배포가 아니다.
- D3 내부: bundle 이외의 7열(release_id,dataset_id,approval_id,target_project_ref,content_sha256,result,created_at), 원출현·검토 payload·구성 문항은 보존한다. 현재 importer는 승인된 입력을 다시 검사한 뒤 저장된 result를 반환한다. 저장 bundle을 읽는 온라인 소비자가 발견되면 구현을 멈추고 설계를 수정한다.
- D4 내부: 기존 보호 함수를 바꾸거나 끄지 않는다. 대상 release trigger만 정확한 거래/연결/원행/다음행 허용을 한 번 소비하게 바꾸고 bundle 이외 열의 변화는 항상 거절한다. 새 내부 함수는 postgres 호출만 허용하며 앱 역할 권한은 없다.
- D5 내부: 한 번에 release 하나, 원행16MiB·파일32MiB·statement30초/lock1초 상한. 실제 운영 읽기 집계(2026-10-03):20행, bundle JSON text129,103,610B, 최대 원행8,773,583B. 이는 압축된 물리 용량이 아니다. 크기 초과는 중단하며 자동 확대하지 않는다.
- D6 내부: 원행을 PostgreSQL JSON 문자열 그대로 외부 파일에 보존한다. bigint를 JavaScript 숫자로 재직렬화하지 않는다. 파일 fsync와 SHA-256 재읽기 확인, 모든 Git 조상 거절, 사본 폴더 접근 확인을 요구한다. 전체 행의 확인값은 `postgres-jsonb-text-sha256-v1`이고 승인 content_sha256은 그대로 둔다.
- D7 내부: 현재 importer와 같은 dataset_key/9129 잠금을 즉시 시도한 뒤 release 행을 NOWAIT로 잠근다. 같은 요청의 완료 결과를 상태 검사보다 먼저 반환하고 잠금 뒤 재확인한다. 후보는 매번 전체 미전환 목록을 새로 읽어 낮은 키의 늦은 등록도 찾는다. MAX(id)는 진행 기준이 아니다.
- D8 내부: 이미 분리된 학습값과 학생 데이터는 변경하지 않으므로 진행 시험에서도 현재 읽기 결과가 동일해야 한다. 일반 앱은 로컬 사본을 읽지 않는다. 신규 importer는 이번에 변경하지 않으며 이후 새 원자료도 파일 보존을 확인한 별도 운영자 처리 대상이다.

준비/적용/복구와 trigger의 시간대는 UTC·날짜 형식은 ISO로 고정한다. DB 사본 파일 SHA, DB 원행 SHA, 승인된 원파일 바이트 SHA, 승인 내용 SHA는 각각 구분한다. 준비 시 저장 bundle의 의미 내용 SHA를 다시 계산하여 bundle/release/approval의 값과 대조한다. 원래 입력 바이트로 등록 재요청을 검사하며 DB 사본으로 원파일 확인을 대신하지 않는다. 운영자는 호출 대상 프로젝트와 파일 targetProjectRef를 외부 연결에서 확인하고 SQL은 해당 release의 target_project_ref와 추가 대조한다.

## 변경 영향

SQL 운영자 준비/전환/복구·원행 확인값·파일 도구·검사와 지도는 변경한다. importer와 등록/학습/학생 조회·캐시는 확인만 한다. UI·브라우저 상태·공개 요청/응답·경로·문구·스타일은 변경하지 않는 내부 도구여서 화면 상태 검사는 해당 없다. 공용48시간/미사용 준비24시간/미접수 답 무기한 보호는 유지한다.

## 검사와 복구

- T1 구형 등록 자료를 새 SQL 직전에 생성, 적용 직후 전열 동일 및 실제 조회/등록 재전송 비교.
- T2 파일 저장/재읽기·변조·큰 정수·Git 밖·1건/크기·잘못된 환경/행 확인값·취소 후 복구.
- T3 대상과 다른 모든 불변 보호·권한·result/승인/학습값/기존 fingerprint 불변.
- T4 실제 두 연결에서 importer 잠금·운영자 경합·같은 요청 재전송·늦은 등록 새 목록 확인.
- T5 두 묶음 중 하나만 파일 복구, 그 사이 접수된 새 학생 답과 비대상 표/다른 묶음의 전열 동일.
- T6 전체 회귀·타입/린트/소유 지도/구조/빌드·검토 DB 적용 전후 보존·독립 검토.

실패 거래는 전체 취소한다. 복구 시 외부 파일에서 지정 원행을 읽어 현재 확인값을 검증한 후 bundle만 되돌린다. 사본이 없거나 불일치하면 복구를 추측하지 않는다. 새 학생 결과나 DB 전체를 예전 시점으로 되돌리지 않는다.
