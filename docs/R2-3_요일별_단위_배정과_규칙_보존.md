# R2-3 요일별 단위 배정과 원 규칙 보존

## 1. 목적과 범위

`회차별` 단어 시험에서 모든 날짜를 1단위로 고정하던 끊긴 연결을 복구한다. 교사가 모든 회차에
같은 단위 수를 쓰거나 월 2단위·수 3단위처럼 요일마다 다른 수를 정하면, 화면부터 Preview·저장·
완료 뒤 다음 시험 생성·최근 조건 복사·배정된 시험 상태까지 같은 의미를 유지한다.

이번 범위에는 일반 단어 시험의 단일·일괄 배정만 포함한다. 독립 오답 시험, 시험 한 건 수정,
학생 자율 시험, 성취 화면과 학부모 PDF는 바꾸지 않는다. Production도 대상이 아니다.

## 2. 확정한 동작

- 입력 방식은 `같은 단위 수 / 요일별 단위 수` 두 가지다.
- 허용값은 회차·요일마다 정수 1~30이다. 0과 31은 화면과 서버가 모두 거부한다.
- 모드를 바꾸거나 요일을 잠시 해제해도 입력했던 정상 숫자는 유지한다.
- 월 2·수 3, 총 8단위의 결과는 `[1,2] / [3,4,5] / [6,7] / [8]`이다.
- 회차 날짜를 옮겨도 단위 수는 옮긴 날짜가 아니라 원래 반복 회차의 요일 규칙을 따른다.
- 첫 시험만 즉시 만들고, 남은 시험은 구체적인 단위 ID와 문제 묶음을 큐에 저장한다. 완료 뒤 다음
  시험을 만들 때 원 규칙으로 다시 계산하지 않는다.
- 원 규칙은 최근 시험 조건 복사와 배정된 시험 상태 설명에 사용한다. 실제 회차 결과에서 역산하지
  않는다.
- 최근 시험 복사에서 저장된 요일 규칙이 있으면 함께 복원한다. 범위·날짜와 `출제 단어 선택`은
  현재 값을 유지한다.

## 3. 서로 다른 두 순서

다음 두 값을 다시 하나로 합치지 않는다.

| 화면 항목 | 내부 값 | 담당 |
|---|---|---|
| 출제 단어 선택 | `source_order / random` | 선택한 범위에서 이번 회차에 넣을 단어를 고른다. |
| 시험 문제 순서 | `ascending / random` | 확정된 문제를 학생 화면에 어떤 순서로 보여 줄지 정한다. |

두 값의 네 조합을 모두 허용한다. `출제 단어 선택`을 바꿔도 시험 문제 순서는 바뀌지 않고,
범위·요일 변경으로 공통 계획을 다시 만들어도 문제 순서를 덮어쓰지 않는다. 예전 `fixed/descending`
문제 순서를 두 버튼 화면으로 복사할 때는 숨은 상태를 남기지 않고 `ascending`으로 정규화한다.

## 4. 저장 계약

브라우저 요청의 `unitAllocationRule`은 다음 버전 자료를 사용한다.

```text
schemaVersion: 1
mode: same | by_weekday
unitsPerSession: 1..30
weekdayUnitsPerSession: 월~일 7개 값, 각각 1..30
```

서버는 원래 반복 일정의 서울 요일에서 회차별 단위 수를 다시 계산하고, 요청의
`rangeUnitCounts`와 실제 `sessions[].unitIds`가 모두 일치해야 저장한다. Preview 계획 해시에는
원 규칙도 들어가므로 결과 단위가 우연히 같아도 `same`과 `by_weekday`는 다른 계획이다.

DB의 series에는 다음을 함께 남긴다.

- `split_basis`
- 버전이 있는 `allocation_rule`과 SHA-256
- Preview에서 확정한 `resolved_plan_sha256`
- 각 회차의 구체적인 `unit_ids`, 문제 snapshot, 공개·마감 시각

DB 함수는 필수 키·7개 요일·1~30·원 반복 요일과 회차 수를 다시 검사한다. 같은 멱등 요청을
재실행해도 `updated_at`을 바꾸지 않아 큐 목록 순서와 페이지 커서를 흔들지 않는다.

## 5. 배포와 복구 순서

쓰기 경로는 원 규칙을 잃지 않기 위해 v3가 없는 DB에서 v2로 조용히 낮추지 않는다. 반드시 다음
순서를 지킨다.

1. Preview DB에 새 migration 한 건을 먼저 적용한다.
2. 구 앱의 queue v2 저장과 summary v1 조회가 계속 되는지 확인한다.
3. 새 앱을 배포해 queue v3 저장과 summary v2 조회를 확인한다.
4. 읽기 RPC가 아직 없는 짧은 구간에는 최근 규칙을 빈 값으로 처리하고 summary v1을 사용해 화면은
   유지한다. 쓰기 RPC가 없으면 `업데이트 중` 오류로 명시적으로 차단한다.

복구할 때는 앱을 queue v2 사용 커밋으로 먼저 되돌리고, 새 v3·조회 v2 실행 권한을 회수한 뒤 새
함수를 제거한다. nullable 규칙·해시 열과 이미 저장된 값은 남긴다. 열 삭제나 과거 migration 수정,
`DROP CASCADE`는 하지 않는다.

## 8. 비용·남은 구조 부채

- 개인 배정과 큐는 `no-store` 성격을 유지한다. 원 규칙 해시는 멱등·감사용이며 캐시 키로 쓰지 않는다.
- 최근 규칙 조회는 모든 과거 assignment ID가 아니라 학생·단어장별 최근 후보 3개만 고른 뒤 500개씩
  조회한다. 전체 학생·단어장 조합 수에 비례하므로 절대 상한이라고 부르지 않는다.
- R3의 목적형 읽기 모델에서는 선택 학생·단어장 기준 지연 조회로 바꾸고, 관리자 이력 전체 조회와
  분리한다.
- 저장된 선택 기능용 규칙 한 행이 손상돼도 전체 화면을 막지 않고 해당 규칙만 제외한 뒤 서버 오류
  기록을 남긴다.

## 10. 2026-08-29 코드·Preview DB 체크포인트

- 공용 순수 계산은 `src/lib/admin/vocab-unit-allocation.ts` 한 곳에 두고 기능 계약은 이를 다시
  내보내는 연결부로 유지했다. 이력·요청·계획 해시는 기능 폴더를 거꾸로 참조하지 않는다.
- Preview 계획 해시는 실제 회차뿐 아니라 배정 방식, 범위 순서, 회차별 단위 수, 요일 규칙,
  남은 범위 처리, 반복 범위 처리, 원 반복 일정과 출제 단어 선택 방식도 함께 묶는다.
- 최근 시험의 요일 규칙을 복사하면 시험일 사용도 함께 켜져, 화면에 보이는 규칙과 실제 저장 계획이
  달라지지 않는다.
- DB는 `schema_version`, 공통 단위 수, 요일, 요일별 단위 수에 JSON 숫자만 허용한다. 숫자처럼
  보이는 문자열은 기존 writer를 부르기 전에 거부하며 아무 행도 남기지 않는다.
- 실제 최종 스키마에서 v3 → 기존 v1 → bulk writer로 가짜 학생 31명의 첫 시험 31개를 만들고,
  series·item·assignment·assigned event가 각각 31개이며 assignment 중복이 0개임을 확인했다.
  같은 요청 재실행은 결과·행 수·이벤트 수·시각을 바꾸지 않고, 같은 멱등키의 규칙·계획 해시 변경은
  `23505`로 거부한다.
- 자동 검증은 305파일·1,643테스트, 구조 경계 48테스트, lint, typecheck,
  `verify:architecture`, Preview 환경 Next.js 16.2.12 build와 `git diff --check`를 통과했다.
- Preview `wojxpruvbjzbhrpmsbuy`에 migration `20260828202720 preserve_vocab_weekday_unit_rules`만
  개별 적용했다. 새 열 4개, v3 writer, 규칙 조회, summary v2와 빈 `search_path`를 읽어 확인했고,
  기존 v2 writer·summary v1도 유지된다. authenticated 앱 역할은 공개 v3만 실행할 수 있고 anon과
  private helper 직접 실행은 차단돼 있다.
- Supabase 보안 권고의 `SECURITY DEFINER` 경고는 새 공개 함수가 authenticated에 열려 있다는
  일반 경고다. 함수 안의 활성 관리자 확인, 빈 `search_path`, PUBLIC·anon 회수와 private helper
  차단을 별도로 확인했다. 이번 migration은 새 표나 인덱스를 만들지 않았다.
- 앱 커밋·자동 Preview 재배포·브라우저 검증은 이 체크포인트 다음 단계다. 완료 전에는 R2-3을
  완료로 올리지 않는다.
