# R2-4 배정 공통 응용 흐름 전환

## 1. 범위

일반 범위 배정, 요일별 범위 배정, 독립 오답 시험, 기존 시험 수정의 미리보기와 저장 수명을 같은
규칙으로 맞춘다. 화면 모양과 R2-3의 요일별 단위 계산은 바꾸지 않는다. 현재 쓰지 않는 예전 일반
단일 생성 화면과 mixed 생성 경로도 되살리지 않는다.

새 DB 객체나 열은 필요하지 않아 migration은 추가하지 않았다. Preview와 Production DB는 이 단계의
로컬 구현·검증 동안 변경하지 않았다.

## 2. 최종 책임 경계

| 위치 | 맡는 일 |
|---|---|
| `application/*-flow-adapter.ts` | 흐름별 요청·응답, 의미 지문, 제출 순간 검증, 충돌 뒤 복구 방식 분류 |
| `application/preview-flow.ts` | 전달받은 최신 요청 확인 함수로 오래된 응답을 버리고 오류 표준화 |
| `application/submission-flow.ts` | 동시 저장 차단, 의미별 멱등키 유지, 제출 시각 한 번 확정 |
| `controller/use-debounced-assignment-preview.ts` | React 입력 지연, 취소 신호와 최신 요청 정책 실행 |
| `controller/use-assignment-controller-runtime.ts` | 배정 화면 공통 현재 시각과 제출 세션 유지 |
| 각 화면 controller | 입력, 탭, focus, 계산 중·오류·완료 표시와 분류된 새 계산·원본 재조회 실행 |
| Route Handler | 인증·same-origin 확인 뒤 명령 시각 한 번 확정 |
| server service·DB | 현재 자료·마감·멱등 요청을 다시 확인하고 원자 저장 |

`application`은 React, JSX, 브라우저 전역과 endpoint 문자열을 직접 갖지 않고 요청 변환기가 만든
URL을 전달받는다. controller에는 endpoint 문자열, 요청 builder·parser, 저장 의미 지문, 업무
validator가 남지 않도록 하위 보조 훅까지 구조 검사로 고정했다.

## 3. 일반 한 명·여러 명 배정

- 한 명과 여러 명은 별도 저장 controller가 아니다. 같은 `useBulkAssignmentController`에 학생 ID
  배열의 크기만 다르게 전달한다.
- `bulk-assignment-flow-adapter.ts`가 미리보기와 저장 요청, 응답 수 검산, 제출 시각 재검사,
  계획 의미 지문과 409 뒤 필요한 복구 방식을 분류한다. controller가 분류에 따라 미리보기를 다시 계산한다.
- 입력이 바뀐 뒤 이전 응답이 늦게 와도 revision·요청 ID·의미 지문이 다른 결과는 버린다.
- 같은 제출을 연속으로 눌러도 한 요청만 실행한다. 일시 오류 재시도는 같은 멱등키를 사용하고,
  실제 배정 조건이 바뀌면 새 키를 만든다.
- 저장 응답의 배정 수가 미리보기의 배정 수와 다르면 성공으로 처리하지 않는다.

요일별 범위와 완료 뒤 이어지는 회차도 이 흐름을 그대로 사용한다. R2-3에서 보존한
`same / by_weekday`, 요일별 단위 수, 실제 회차 범위와 큐 연결은 변경하지 않는다.

## 4. 독립 오답 시험

- 오답 요약 조회, 미리보기, 저장 오류 해석을 `direct-review-flow-adapter.ts`로 모았다.
- 현재 후보가 달라진 409만 요약과 미리보기를 다시 읽는다. 같은 멱등키를 다른 요청에 쓴 오류는
  자동 새로고침으로 숨기지 않는다.
- Route는 두 충돌을 `review_candidates_changed`, `idempotency_key_reused`로 구분한다.
- same-origin, 관리자 세션 없음, 권한 거부를 각각 403·401·403으로 유지한다.
- 마감과 업무 검증은 창을 연 때가 아니라 저장 버튼을 누른 순간 다시 실행한다.

## 5. 기존 시험 수정

- `assignment-edit-flow-adapter.ts`가 수정 원본 GET, 문항 수 미리보기, PUT 저장, 요청·응답 해석과
  충돌 뒤 필요한 복구 방식을 분류한다. controller가 분류에 따라 원본을 다시 읽거나 미리보기를 다시 계산한다.
- 409가 원본 변경을 뜻하면 문항 수만 다시 계산하지 않고 수정 원본 GET을 다시 읽어 초안과 기준본을
  함께 교체한다. 오래된 문제 묶음·오답 대기열을 계속 편집하지 않는다.
- 서버 422의 `fieldPath`를 보존해 마감 같은 실제 입력 위치에 오류를 연결한다.
- Route가 읽은 명령 시각 하나를 수정 원본 준비와 교체 저장까지 그대로 전달한다.
- R2-2의 미래 공개 시각, mixed·exact 문제 snapshot, 선택지, 오답 queue ID, series item 보존 규칙은
  그대로 유지한다.
- 입력 버튼 동작은 `single-assignment-controller-actions.ts`로 분리했다. 현재 시각과 제출 세션은
  다른 배정 controller와 공통 실행 보조 훅을 사용한다.

## 6. Next.js·React 적용 기준

- 저장과 미리보기는 개인·진행 자료라 요청 사이 캐시하지 않는다. 성공 결과를 Client 캐시에 따로
  복제하지 않고 server·DB의 멱등 기록을 최종 기준으로 사용한다.
- Route Handler는 인증과 명령 경계만 맡고, 업무 계산은 server service와 순수 계약에 둔다.
- 기존 Server Component, `loading.tsx`, 상세 경계의 점진 표시는 바꾸지 않았다. 이 배치는 Client
  요청 수명 정리이므로 새 전체 화면 Client 영역이나 새 전역 캐시를 만들지 않았다.
- 수정 controller는 718줄에서 입력 동작을 분리해 621줄이 됐다. 줄 수를 절대 제한으로 쓰지 않고,
  입력 동작·공통 실행 수명·흐름별 요청 계약이라는 책임 단위로 나눴다.
- 기능 소유권 지도에는 범위·요일·오답·수정·이어지는 배정에서 공통 응용 흐름과 controller 보조 훅의
  실제 import 경로를 기록했다.
